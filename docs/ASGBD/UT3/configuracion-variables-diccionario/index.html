3.2. Configuración del servidor

Para modificar un ajuste necesitamos distinguir lo que está escrito en la configuración, el valor que utiliza ahora el servidor y lo que ocurrirá al reiniciarlo. En este apartado localizamos los archivos de opciones, consultamos variables y realizamos cambios de prueba que después revertimos.

Dónde trabajamos

Ejecutamos los comandos de Windows dentro de la VM. Las consultas SQL se realizan en una conexión local de MySQL con root.

Cuando indicamos Símbolo del sistema, utilizamos cmd.exe. Cuando indicamos consola MySQL, escribimos después de mysql>. No copiamos esos indicadores como parte de las instrucciones.

1️⃣ Localizamos la configuración​

MySQL Server puede recibir opciones al arrancar y leerlas desde archivos. En una instalación habitual con MySQL Installer encontramos my.ini en:

C:\ProgramData\MySQL\MySQL Server 8.0\my.ini

Es una ruta de referencia: comprobamos cuál utiliza nuestro servicio. ProgramData suele estar oculta; podemos escribir la ruta en la barra del Explorador.

En el Símbolo del sistema ejecutamos:

sc.exe qc MySQL80
en este ejemplo

qc consulta la configuración del servicio. En BINARY_PATH_NAME buscamos mysqld.exe y la opción --defaults-file, que identifica el archivo de opciones indicado para ese servicio. MySQL80 es el nombre habitual; si elegimos otro durante la instalación, lo sustituimos.

Utilizamos sc.exe para identificar expresamente la herramienta de Windows, también si ejecutamos la orden desde PowerShell.

También podemos abrir services.msc, localizar el servicio y consultar Propiedades → General → Ruta de acceso al ejecutable.

🔶 Qué contiene my.ini​

Las opciones se agrupan mediante nombres entre corchetes. Este fragmento simplificado ilustra su estructura; no sustituimos nuestro archivo por él:

[client]
port=3306

[mysql]
no-beep

[mysqld]
port=3306
max_connections=151
GrupoA quién se aplicaOpción del ejemploQué significa
[client]Clientes que lean este grupo.port=3306Utilizan el puerto 3306 para conectarse, salvo que indiquemos otro.
[mysql]Cliente de consola mysql.no-beepDesactiva el aviso sonoro que puede emitir la consola ante un error. No necesita un valor numérico.
[mysqld]Servidor MySQL.port=3306El servidor escucha las conexiones del protocolo clásico en el puerto TCP 3306.
[mysqld]Servidor MySQL.max_connections=151Establece un límite general de 151 conexiones simultáneas.

El puerto aparece en dos grupos porque cumple funciones distintas: en el cliente indica a qué puerto conectarse; en el servidor, en qué puerto escuchar. Ambos deben coincidir para establecer la conexión.

Las líneas que empiezan por # son comentarios. Que una opción del cliente figure en el archivo del servidor no garantiza que un cliente instalado en otro equipo lea ese archivo: cada programa utiliza sus propios archivos y opciones.

Antes de editar my.ini, guardamos una copia y registramos el cambio previsto. Lo abrimos con permisos suficientes y conservamos su formato. Las modificaciones del archivo requieren reiniciar el servidor para aplicarse; veremos cómo hacerlo en el apartado 3.3.

2️⃣ Consultamos los valores efectivos​

El valor efectivo es el que MySQL está utilizando en este momento. Para consultarlo, entramos en la consola MySQL y ejecutamos:

SELECT VERSION(), @@hostname, @@port;
SHOW GLOBAL VARIABLES LIKE 'max_connections';
SHOW GLOBAL VARIABLES LIKE '%timeout%';
en este ejemplo

La primera consulta identifica el servidor. SHOW GLOBAL VARIABLES consulta ajustes globales; LIKE permite buscar un nombre o utilizar % como comodín. Las consultas no modifican la configuración.

También podemos obtener un valor mediante SELECT @@GLOBAL.nombre_variable.

🔶 Global y de sesión​

Una sesión es el contexto de una conexión abierta con MySQL. Tiene sus propios ajustes, que pueden diferir de los de otras conexiones.

ÁmbitoQué significaEjemplo
GlobalAjuste del servidor; en variables que también tienen ámbito de sesión, normalmente sirve para inicializar sesiones nuevas.max_connections solo tiene ámbito global.
SesiónAjuste de la conexión actual.sql_mode tiene valor global y de sesión.
SELECT @@GLOBAL.sql_mode, @@SESSION.sql_mode;

sql_mode reúne reglas que influyen en cómo MySQL interpreta y comprueba determinadas instrucciones y datos. Aquí solo comparamos sus valores global y de sesión, sin modificar ni estudiar cada regla.

No todas las variables admiten ambos ámbitos. Además, global no significa persistente: el ámbito indica a qué afecta el valor; la persistencia indica si queda guardado para otros arranques.

🔶 Cambios en marcha o al arrancar​

Las variables dinámicas admiten cambios con el servidor iniciado. Otras, como port, requieren configurar el arranque y reiniciar. Consultamos en la documentación de cada variable su ámbito, si es dinámica, su unidad y los valores admitidos.

3️⃣ Probamos un cambio de sesión​

Utilizamos sql_safe_updates, una variable de sesión del servidor que ayuda a evitar determinados UPDATE o DELETE sin condiciones adecuadas. Algunos clientes pueden activarla al conectarse. UPDATE modifica filas y DELETE las elimina. Aquí solo observamos el ámbito de la variable: no ejecutamos modificaciones de datos.

En una primera conexión, que llamaremos A:

SET @valor_inicial = @@SESSION.sql_safe_updates;
SELECT CONNECTION_ID(), @@SESSION.sql_safe_updates;
SET SESSION sql_safe_updates = 1;
SELECT CONNECTION_ID(), @@SESSION.sql_safe_updates;
en este ejemplo

Guardamos el valor inicial en una variable de usuario, @valor_inicial, que pertenece a esta sesión. Después asignamos 1 a sql_safe_updates. Si ya valía 1, no veremos una diferencia: la instrucción simplemente confirma ese valor.

CONNECTION_ID() identifica la conexión y nos ayuda a distinguir las sesiones.

Abrimos otra consola MySQL, conexión B, y consultamos:

SELECT CONNECTION_ID(), @@SESSION.sql_safe_updates;

B tiene otro identificador y sus propios valores. Puede mostrar el mismo valor que A, pero el cambio de A no se ha trasladado a B.

Al terminar, recuperamos el valor en A, sin cerrar antes esa conexión:

SET SESSION sql_safe_updates = @valor_inicial;
SELECT @@SESSION.sql_safe_updates;

4️⃣ Diferenciamos cambio global y persistencia​

Global indica el ámbito del ajuste: pertenece al servidor y, según la variable, afecta a su funcionamiento o establece el valor inicial de las sesiones nuevas. No significa que quede guardado.

Persistido significa que hemos guardado un valor para que MySQL lo cargue en los siguientes arranques. Ese valor puede coincidir o no con el que está utilizando ahora el servidor.

Por tanto, distinguimos dos preguntas:

  • Ámbito: ¿a qué afecta el ajuste: al servidor o a nuestra sesión?
  • Persistencia: ¿queda guardado para los siguientes arranques?

Con SET GLOBAL cambiamos el valor global actual. Con SET PERSIST cambiamos ese valor y, además, lo guardamos.

InstrucciónEfecto
SET SESSIONCambia el valor de la sesión actual.
SET GLOBALCambia el valor global en ejecución; no lo guarda para futuros arranques.
SET PERSISTCambia un valor global y lo guarda para futuros arranques.
SET PERSIST_ONLYGuarda un valor para futuros arranques sin cambiar el efectivo. Su disponibilidad depende de la variable.
RESET PERSISTRetira un ajuste persistido; no modifica por sí solo el valor efectivo.

Un cambio global puede afectar al funcionamiento del servidor inmediatamente o servir de valor inicial para sesiones nuevas, según la variable. No suponemos que todas se comportan igual.

🔶 Dónde se guarda lo persistido​

SET PERSIST guarda ajustes en mysqld-auto.cnf, dentro del directorio de datos; no edita my.ini. Consultamos los ajustes guardados mediante:

SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.persisted_variables
ORDER BY VARIABLE_NAME;

Para las variables persistidas que utilizaremos, sus valores se cargan después de los archivos de opciones y tienen prioridad sobre los de my.ini. No editamos mysqld-auto.cnf manualmente.

🔶 Ejemplo de cambio global y persistente​

Utilizamos max_connections. El valor 50 es únicamente de demostración: no es una recomendación para cualquier servidor.

Primero registramos el valor efectivo y comprobamos si ya está persistido:

SELECT @@GLOBAL.max_connections;

SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.persisted_variables
WHERE VARIABLE_NAME = 'max_connections';

Si la segunda consulta no devuelve filas, no hay un ajuste persistido para esa variable. Si devuelve una fila, anotamos también su valor.

SET GLOBAL max_connections = 50;
SELECT @@GLOBAL.max_connections;

SET PERSIST max_connections = 50;

SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.persisted_variables
WHERE VARIABLE_NAME = 'max_connections';
en este ejemplo

SET GLOBAL cambia el límite actual. SET PERSIST deja ese mismo límite guardado para futuros arranques. Comprobamos por separado el valor efectivo y el persistido.

Estas operaciones requieren privilegios administrativos; las realizamos localmente con root.

🔶 Recuperamos el estado anterior​

Si no existía un ajuste persistido, retiramos el que añadimos:

RESET PERSIST IF EXISTS max_connections;

Después recuperamos el valor efectivo inicial. Solo si habíamos registrado 151, ejecutamos:

SET GLOBAL max_connections = 151;

Si ya existía un ajuste persistido, lo restauramos mediante SET PERSIST con su valor anterior. Si el valor efectivo inicial era diferente, lo recuperamos después con SET GLOBAL.

Comprobamos de nuevo ambas consultas. Recuperar el estado anterior significa restaurar el funcionamiento actual y la configuración guardada. No utilizamos un valor por defecto como sustituto del valor que realmente encontramos.

La comprobación después de reiniciar se realizará cuando trabajemos el control del servicio en 3.3. Las variables de usuario como @valor_inicial se pierden al desconectarnos: para una intervención con reinicio necesitamos el registro escrito.

5️⃣ Averiguamos el origen del valor​

performance_schema.variables_info informa del origen desde el que se estableció más recientemente una variable:

SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.global_variables
WHERE VARIABLE_NAME IN ('port', 'max_connections')
ORDER BY VARIABLE_NAME;

SELECT VARIABLE_NAME, VARIABLE_SOURCE, VARIABLE_PATH
FROM performance_schema.variables_info
WHERE VARIABLE_NAME IN ('port', 'max_connections')
ORDER BY VARIABLE_NAME;
en este ejemplo

La primera consulta muestra los valores efectivos. La segunda muestra su origen y, cuando corresponde, la ruta del archivo. Relacionamos ambas salidas mediante VARIABLE_NAME. IN selecciona los dos nombres indicados y ORDER BY ordena las filas por nombre.

OrigenInterpretación
COMPILEDValor incorporado por defecto en el programa.
EXPLICITProcede del archivo indicado mediante --defaults-file.
COMMAND_LINESe estableció mediante las opciones de arranque.
PERSISTEDSe cargó desde la configuración persistida.
DYNAMICSe modificó durante la ejecución.

Existen otros orígenes asociados a distintas formas de leer archivos de opciones. La captura siguiente reúne la misma información en una sola salida. En las consultas anteriores la obtenemos en dos pasos.

DYNAMIC no significa «sin guardar»

Una variable cambiada con SET PERSIST puede aparecer como DYNAMIC, porque se modificó durante la ejecución. Para saber si está guardada, consultamos también performance_schema.persisted_variables.

6️⃣ Consultamos el diccionario y la información del sistema​

El diccionario de datos describe los objetos que gestiona MySQL: esquemas, tablas, columnas y restricciones, entre otros. En MySQL 8.0 sus tablas internas no se consultan directamente; utilizamos interfaces como INFORMATION_SCHEMA.

También disponemos de otros esquemas del sistema con información administrativa y de actividad:

EsquemaPara qué lo utilizamos
information_schemaConsultar metadatos: bases de datos, tablas, columnas, restricciones y motores.
performance_schemaConsultar información de ejecución y configuración, como las variables utilizadas en este apartado.
mysqlConsultar información administrativa, como cuentas y privilegios, cuando tengamos autorización.
sysUtilizar vistas que facilitan el diagnóstico; las desarrollaremos en unidades posteriores.

No todos estos esquemas son el diccionario de datos interno. Los diferenciamos por su función y no modificamos sus tablas para configurar cuentas u objetos: utilizamos las instrucciones administrativas correspondientes.

🔶 De la consulta rápida a la consulta detallada​

SHOW DATABASES;

SELECT SCHEMA_NAME, DEFAULT_CHARACTER_SET_NAME,
       DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA
ORDER BY SCHEMA_NAME;
en este ejemplo

SHOW DATABASES permite consultar rápidamente las bases visibles para la cuenta. La segunda consulta añade sus valores por defecto de caracteres y cotejamiento. Los nombres de las columnas describen qué información devuelve cada fila.

Para consultar las tablas de una base, sustituimos nombre_base por su nombre real:

SELECT TABLE_NAME, ENGINE, TABLE_COLLATION
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'nombre_base'
  AND TABLE_TYPE = 'BASE TABLE'
ORDER BY TABLE_NAME;

Estas consultas nos permitirán comprobar las decisiones sobre motores y texto en 3.4.

🔶 Configuración y actividad son diferentes​

Las variables del sistema contienen ajustes. Las variables de estado informan de la actividad:

SHOW GLOBAL VARIABLES LIKE 'max_connections';
SHOW GLOBAL STATUS LIKE 'Threads_connected';

La primera indica el límite configurado; la segunda, cuántas conexiones hay abiertas en ese momento. Esta diferencia será útil al comprobar los parámetros de conexión.

7️⃣ Qué debemos distinguir antes de continuar​

  • Archivo de opciones: configuración que el programa lee al arrancar.
  • Valor efectivo: ajuste utilizado en este momento.
  • Ámbito: servidor o sesión al que afecta.
  • Persistencia: configuración guardada para futuros arranques.
  • Metadatos y estado: información que consultamos para conocer el sistema y comprobar los resultados.
