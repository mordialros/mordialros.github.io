3.5. Parámetros de conexión

Cada cliente que trabaja con MySQL Server mantiene una conexión. El servidor dedica recursos a cada una mientras está abierta, aunque no realice operaciones. En este apartado aprenderemos a limitar el número de conexiones, a cerrar las inactivas y a comprobar el efecto de estos ajustes.

1️⃣ Observamos las conexiones​

SHOW PROCESSLIST;

Cada fila es una conexión: su identificador, la cuenta, el equipo de origen, la base de datos, el tipo de orden que ejecuta y los segundos que lleva en ese estado. Las conexiones inactivas aparecen con Command = Sleep.

[IMAGEN. Resultado de SHOW PROCESSLIST con varias conexiones, alguna en estado Sleep y la propia consulta en Query.]

Las variables de estado resumen la actividad:

SHOW GLOBAL STATUS LIKE 'Threads_connected';      -- conexiones abiertas ahora
SHOW GLOBAL STATUS LIKE 'Max_used_connections';   -- máximo simultáneo desde el arranque
SHOW GLOBAL STATUS LIKE 'Connection_errors_max_connections';  -- rechazos por límite
SHOW GLOBAL STATUS LIKE 'Aborted_c%';             -- conexiones fallidas o cerradas de forma anómala

Max_used_connections es un buen dato para decidir un límite: indica cuántas conexiones se han necesitado realmente.

2️⃣ Número máximo de conexiones​

max_connections establece cuántas conexiones simultáneas acepta el servidor. Su valor por defecto es 151.

SELECT @@max_connections;

Cuando se alcanza el límite, las nuevas conexiones se rechazan:

ERROR 1040 (HY000): Too many connections
Una conexión reservada para administrar

MySQL acepta en realidad una conexión más que el límite, reservada para cuentas con el privilegio CONNECTION_ADMIN, como root. Así podemos entrar a diagnosticar el problema aunque el servidor esté saturado. Si root ya ocupa esa conexión, también será rechazado.

🔸 Cómo decidimos el valor​

El límite no es el número de personas que trabajan. Para decidirlo tenemos en cuenta:

  • Las conexiones de trabajo previstas en los momentos de mayor actividad.
  • Las conexiones de administración y supervisión.
  • Las herramientas cliente: algunas abren más de una conexión por cada ventana o pestaña.
  • Las aplicaciones que mantienen varias conexiones abiertas para reutilizarlas.
  • Un margen razonable para picos o reconexiones.
  • Los recursos del servidor: cada conexión consume memoria.

Un valor muy alto no mejora el servicio: permite que un número excesivo de conexiones agote la memoria del servidor. Un valor muy bajo provoca rechazos.

Límite por cuenta

max_user_connections limita las conexiones simultáneas de cada cuenta. Su valor 0 significa «sin límite». También pueden establecerse límites para una cuenta concreta; lo veremos al trabajar con cuentas en UT4.

🔸 Comprobamos el límite​

Para comprobar el efecto sin afectar a la configuración definitiva, aplicamos un valor temporal muy bajo con SET GLOBAL, provocamos el rechazo y recuperamos el valor:

-- 1. Registramos el valor actual
SELECT @@max_connections;

-- 2. Valor de prueba, sin persistir
SET GLOBAL max_connections = 3;

Abrimos varias consolas con una cuenta sin privilegios de administración hasta superar el límite y observamos el error 1040. Después comprobamos que root todavía puede conectarse usando la conexión reservada.

-- 3. Recuperamos el valor registrado o el requerido
SET GLOBAL max_connections = 151;
SHOW GLOBAL STATUS LIKE 'Connection_errors_max_connections';

[IMAGEN. Consola con ERROR 1040 Too many connections al intentar conectar con una cuenta sin privilegios.]

3️⃣ Tiempos de espera​

VariableQué controlaPor defecto
wait_timeoutSegundos que una conexión no interactiva puede permanecer inactiva antes de que el servidor la cierre.28800 (8 h)
interactive_timeoutLo mismo para conexiones interactivas.28800 (8 h)
connect_timeoutSegundos que el servidor espera a que un cliente complete el inicio de la conexión.10

🔸 Interactiva o no interactiva​

Al conectarse, cada cliente indica si es interactivo, es decir, si lo utiliza una persona escribiendo órdenes. El servidor inicializa el wait_timeout de sesión de la conexión así:

  • Si el cliente es interactivo: con el valor global de interactive_timeout.
  • Si no es interactivo: con el valor global de wait_timeout.

Por tanto, el valor que realmente se aplica a una conexión es siempre su wait_timeout de sesión, pero puede proceder de variables globales distintas.

SELECT @@global.wait_timeout, @@global.interactive_timeout, @@session.wait_timeout;

La consola mysql abierta normalmente es interactiva. Con la opción -e, el cliente ejecuta las sentencias indicadas en modo no interactivo y termina:

mysql -u cuenta -p -e "SELECT @@session.wait_timeout"

Las aplicaciones y las herramientas gráficas declaran su propio tipo. No lo suponemos: lo comprobamos consultando @@session.wait_timeout desde cada cliente.

🔸 Comprobamos el cierre por inactividad​

Podemos observar el efecto en nuestra propia sesión con un valor pequeño:

SET SESSION wait_timeout = 10;
-- Esperamos 15 segundos sin escribir nada y ejecutamos:
SELECT 1;

El servidor ha cerrado la conexión. El cliente nos informa de ello:

ERROR 4031 (HY000): The client was disconnected by the server because of inactivity. See wait_timeout and interactive_timeout for configuring this behavior.
No connection. Trying to reconnect...

La consola mysql se reconecta automáticamente. La nueva conexión es una sesión nueva y vuelve a tomar el valor global: lo comprobamos de nuevo con SELECT @@session.wait_timeout;.

[IMAGEN. Consola mysql con SET SESSION wait_timeout = 10, el error 4031 tras la espera y la reconexión automática.]

Tiempos muy cortos

Un wait_timeout demasiado bajo puede cerrar conexiones que una aplicación espera reutilizar y provocar errores en ella. Lo ajustamos según el requisito y comprobamos el comportamiento de los clientes que lo utilizan.

4️⃣ Errores de conexión repetidos​

Si un equipo provoca muchos intentos de conexión fallidos e interrumpidos, el servidor bloquea ese equipo cuando supera max_connect_errors (por defecto, 100):

ERROR 1129 (HY000): Host '192.168.10.1' is blocked because of many connection errors

Para desbloquearlo vaciamos la caché de equipos:

TRUNCATE TABLE performance_schema.host_cache;

El contador se refiere a intentos que se interrumpen sin llegar a completar la conexión, por ejemplo por problemas de red o clientes mal configurados, y se reinicia cuando el equipo se conecta correctamente.

5️⃣ Aplicamos y documentamos​

Para cada parámetro de conexión registramos:

  1. El valor inicial y su origen (performance_schema.variables_info).
  2. El valor requerido y su justificación.
  3. El ámbito del cambio y si debe conservarse (SET PERSIST).
  4. La prueba realizada en una conexión nueva y su resultado.
  5. Cómo recuperaríamos el valor inicial.
Idea clave

Los límites de conexión protegen al servidor. Los decidimos a partir del uso real y de los recursos, y siempre comprobamos su efecto con conexiones nuevas.
