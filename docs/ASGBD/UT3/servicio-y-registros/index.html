3.3. Inicio, parada y registros

En UT2 comprobamos que MySQL funcionaba como servicio de Windows. Ahora estudiamos cómo debe iniciarse, en qué condiciones podemos detenerlo y cómo comprobamos lo ocurrido mediante sus registros.

Dónde trabajamos

Trabajamos dentro de la VM. Las consultas SQL se ejecutan en una conexión local con root. Para modificar o iniciar y detener servicios desde Windows, abrimos la herramienta con permisos de administrador.

El nombre de servicio utilizado en los ejemplos es MySQL80. Si nuestra instalación utiliza otro, lo sustituimos.

1️⃣ Tipo de inicio y estado del servicio​

Son dos propiedades diferentes:

  • Tipo de inicio: cómo está previsto que arranque el servicio.
  • Estado: si está ejecutándose o detenido en este momento.

Un servicio puede estar configurado como automático y encontrarse detenido. Cambiarlo a manual tampoco detiene el proceso que ya está ejecutándose.

🔶 Consultamos desde Servicios​

  1. Pulsamos Windows + R dentro de la VM.
  2. Escribimos services.msc y pulsamos Intro.
  3. Localizamos MySQL80 y abrimos sus propiedades.
  4. Consultamos Tipo de inicio y Estado del servicio.
Tipo de inicioComportamiento
AutomáticoWindows intenta iniciarlo durante el arranque.
Automático (inicio retrasado)Windows retrasa su inicio respecto a otros servicios automáticos.
ManualNo se inicia automáticamente por ese ajuste. Podemos iniciarlo cuando lo necesitemos.
DeshabilitadoNo permite iniciarlo hasta cambiar el tipo de inicio.

Para un servidor que debe estar disponible al arrancar la VM elegimos Automático. Si ya está así, lo comprobamos sin cambiarlo innecesariamente. La disponibilidad real también depende de que el arranque termine correctamente.

🔶 Alternativa con comandos​

En el Símbolo del sistema:

sc.exe qc MySQL80
sc.exe query MySQL80

La primera orden consulta la configuración. La segunda muestra el estado: RUNNING significa en ejecución y STOPPED, detenido. Los nombres de los campos pueden aparecer traducidos.

Si necesitamos cambiar el inicio, ejecutamos solo la opción elegida desde cmd.exe como administrador:

InicioComando
Automáticosc.exe config MySQL80 start= auto
Manualsc.exe config MySQL80 start= demand

En esta sintaxis dejamos un espacio después de start=. También podemos gestionar el servicio con los comandos de PowerShell Get-Service, Set-Service, Start-Service y Stop-Service.

2️⃣ Preparamos una parada controlada​

Detener el servidor interrumpe el servicio para todos sus clientes. Antes de una intervención:

  1. Identificamos el servidor y acordamos el momento de mantenimiento.
  2. Avisamos a quienes lo utilizan y coordinamos que no comiencen nuevas operaciones.
  3. Revisamos conexiones y trabajo en curso.
  4. Dejamos finalizar o gestionamos las operaciones pendientes según el procedimiento establecido.
  5. Preparamos las comprobaciones de arranque y la reversión de los cambios previstos.

En la consola MySQL podemos consultar:

SHOW PROCESSLIST;

Cada fila aporta información de una sesión o hilo del servidor. Una cuenta con permisos limitados puede ver solo sus propias conexiones. Sleep indica que una conexión está esperando una nueva orden, pero no garantiza por sí solo que no tenga una transacción abierta. Una transacción agrupa cambios que pueden estar pendientes de confirmar o deshacer. Explicaremos su funcionamiento básico en 3.4.

En esta práctica trabajamos únicamente con nuestras sesiones conocidas: terminamos las tareas previas y cerramos los clientes de prueba que no necesitemos. SHOW PROCESSLIST nos ayuda a identificar conexiones, pero no basta para asegurar que no quedan transacciones pendientes. El diagnóstico completo de esas operaciones se desarrollará más adelante, al estudiar transacciones y concurrencia.

Parada normal y cierre forzado

No utilizamos el Administrador de tareas para terminar mysqld.exe como procedimiento habitual. Una parada normal permite al servidor cerrar conexiones, deshacer transacciones pendientes cuando corresponda y completar sus tareas de cierre. Una terminación brusca puede requerir recuperación en el siguiente arranque.

Cerrar la consola o Workbench solo cierra el cliente: no detiene MySQL Server.

3️⃣ Detenemos, iniciamos y comprobamos​

🔶 Procedimiento desde Windows​

Permisos de administrador en Windows

Para detener o iniciar el servicio necesitamos abrir el Símbolo del sistema como administrador, dentro de la VM.

Pulsamos Windows + R, escribimos cmd y, en lugar de pulsar Intro, usamos Ctrl + Mayús + Intro. Aceptamos el aviso de Windows y comprobamos que el título de la ventana incluye Administrador.

Si aparece «Error de sistema 5. Acceso denegado», comprobamos que hemos abierto la consola con estos permisos. Si Windows solicita credenciales, debemos utilizar una cuenta administradora de Windows, no la contraseña de root de MySQL.

En el Símbolo del sistema como administrador, dentro de la VM, detenemos el servicio:

net stop MySQL80

Cuando termine, consultamos su estado:

sc.exe query MySQL80

Comprobamos que aparece STOPPED. Si aparece STOP_PENDING, esperamos unos segundos y repetimos la consulta.

Después iniciamos el servicio:

net start MySQL80

Cuando termine, consultamos de nuevo su estado:

sc.exe query MySQL80

Comprobamos que aparece RUNNING. Podemos realizar las mismas operaciones con los botones Detener e Iniciar de Servicios.

🔶 Alternativa desde MySQL​

Una sesión con el privilegio necesario puede solicitar una parada mediante:

SHUTDOWN;

Para comprobarlo, intentamos ejecutar una consulta en la misma consola:

SELECT 1;

El cliente detecta que ha perdido la conexión e intenta reconectarse. Como el servidor sigue detenido, el intento falla:

ERROR 2013 (HY000): Lost connection to MySQL server during query
No connection. Trying to reconnect...
ERROR 2003 (HY000): Can't connect to MySQL server on 'localhost:3306' (10061)
ERROR:
Can't connect to the server
en este ejemplo

El error 2013 indica que se ha perdido la conexión. Después, el cliente intenta recuperarla, pero recibe el error 2003 porque no puede conectarse al servidor detenido.

La consola sigue abierta, pero no dispone de una conexión activa. Los mensajes pueden variar según el cliente y el momento en que detecte la desconexión.

Confirmamos la parada desde el Símbolo del sistema de la VM con sc.exe query MySQL80: el estado debe ser STOPPED.

Para volver a iniciarlo, ejecutamos net start MySQL80 en el Símbolo del sistema como administrador. No podemos iniciar desde una sesión SQL un servidor que está detenido.

🔶 Verificamos el arranque​

Abrimos una conexión MySQL nueva y ejecutamos:

SELECT VERSION(), @@hostname, @@port;
SHOW GLOBAL STATUS LIKE 'Uptime';

Uptime indica los segundos transcurridos desde el arranque. Un valor pequeño es coherente con un inicio reciente, pero completamos la comprobación con el estado del servicio y el registro.

Si reiniciamos para aplicar una configuración, consultamos también las variables afectadas y probamos el comportamiento previsto. La configuración persistente estudiada en 3.2 se verifica tras el arranque comparando el valor efectivo con el guardado, cuando proceda.

4️⃣ Diferenciamos los registros​

Un registro o log conserva información sobre sucesos del servidor o peticiones recibidas. Elegimos cuál consultar según el problema.

RegistroFunciónAlcance en esta unidad
ErroresInforma de arranques, paradas, advertencias y errores del servidor.Localizamos, leemos e interpretamos mensajes.
GeneralRegistra conexiones y sentencias recibidas.Lo activamos brevemente para una comprobación.
Consultas lentasRecoge consultas según los umbrales y opciones establecidos.Reconocemos su función. Lo desarrollaremos en rendimiento.
BinarioRegistra cambios utilizados en replicación y recuperación.Reconocemos su función. Lo desarrollaremos en las unidades correspondientes.

Antes de abrir los registros, consultamos su ubicación y comprobamos cuáles están activados. Ejecutamos estas instrucciones en la consola de MySQL, conectados como root.

SELECT @@GLOBAL.log_error, @@GLOBAL.datadir;
en este ejemplo

Consultamos dos valores del servidor:

  • log_error: indica el nombre o la ruta del archivo del registro de errores.
  • datadir: indica la carpeta donde MySQL almacena sus datos.

Si log_error muestra una ruta completa, podemos utilizarla directamente. Si muestra solo un nombre, como SERVIDOR.err, el archivo se encuentra dentro de la carpeta indicada por datadir.

La carpeta ProgramData puede estar oculta

En Windows, la carpeta C:\ProgramData suele estar oculta. Aunque no la veamos en el Explorador, podemos acceder directamente.

Dentro de la VM, copiamos la ruta obtenida en datadir, la pegamos en la barra de direcciones del Explorador de archivos y pulsamos Intro.

También podemos pulsar Windows + R, pegar esa ruta y pulsar Intro. Si Windows solicita permiso para acceder, pulsamos Continuar.

No debemos confundir C:\ProgramData, donde esta instalación guarda los datos y registros, con C:\Program Files, donde se encuentran los ejecutables.

SHOW GLOBAL VARIABLES LIKE 'general_log%';
en este ejemplo

Mostramos las variables cuyo nombre empieza por general_log. El símbolo % permite buscar cualquier continuación del nombre.

  • general_log: indica si el registro general está activado (ON) o desactivado (OFF).
  • general_log_file: indica el archivo utilizado cuando el registro se escribe en un archivo.

Este registro recoge las conexiones y las instrucciones recibidas por el servidor.

SHOW GLOBAL VARIABLES LIKE 'slow_query_log%';
en este ejemplo

Consultamos la configuración del registro de consultas lentas:

  • slow_query_log: indica si está activado (ON) o desactivado (OFF).
  • slow_query_log_file: indica el archivo utilizado cuando el registro se escribe en un archivo.

Este registro ayuda a localizar consultas que cumplen las condiciones configuradas para considerarlas lentas.

SHOW GLOBAL VARIABLES LIKE 'log_bin%';
en este ejemplo

Consultamos las variables relacionadas con el registro binario:

  • log_bin: indica si está activado (ON) o desactivado (OFF).
  • log_bin_basename: indica la ruta y el nombre base de sus archivos.
  • log_bin_index: indica el archivo que contiene la lista de archivos del registro binario.

El registro binario recoge eventos de cambios en los datos y la estructura. Se utiliza para la replicación y, junto con una copia de seguridad, para recuperar cambios posteriores a esa copia.

Destino del registro general y del registro de consultas lentas

Que aparezca un nombre de archivo no significa que el registro esté activado ni que se esté escribiendo en ese archivo. La variable log_output determina si estos registros se envían a archivos (FILE), a tablas (TABLE), a ambos o a ninguno (NONE).

Podemos consultarla con SHOW GLOBAL VARIABLES LIKE 'log_output';.

5️⃣ Leemos el registro de errores​

🔶 Localizamos y abrimos el archivo​

  1. Consultamos @@GLOBAL.log_error y @@GLOBAL.datadir.
  2. Localizamos el archivo en el Explorador de la VM.
  3. Lo abrimos con un editor de texto, sin modificarlo.
  4. Buscamos los mensajes correspondientes a nuestra parada y arranque por su fecha y hora.

También podemos leer las últimas líneas del registro desde PowerShell, dentro de la VM. En el siguiente comando, sustituimos la ruta de ejemplo por la ruta completa de nuestro archivo de registro, obtenida con log_error y datadir.

Get-Content "C:\ProgramData\MySQL\MySQL Server 8.0\Data\SERVIDOR.err" -Tail 30
en este ejemplo

Get-Content lee el contenido del archivo y -Tail 30 muestra únicamente sus últimas 30 líneas. Así consultamos los mensajes recientes sin abrir todo el registro.

🔶 Interpretamos un mensaje​

Ejemplo simplificado del contenido de una línea:

2026-10-19T08:15:02.512345Z 0 [System] [MY-010931] [Server] ... ready for connections ... port: 3306 ...
ParteQué aporta
Fecha y horaMomento del suceso. La Z indica UTC.
Identificador de hiloContexto del servidor que genera el mensaje.
PrioridadTipo de mensaje: sistema, error, advertencia o nota.
Código MY-...Identificador para consultar su significado en la documentación.
SubsistemaComponente que informa, como Server o InnoDB.
TextoDescripción concreta del suceso.

ready for connections indica que el servidor está preparado para aceptar conexiones. Para la parada buscamos mensajes como Shutdown complete. La redacción exacta y las líneas intermedias pueden variar.

Consultamos la referencia temporal antes de relacionar el registro con el reloj de Windows:

SHOW GLOBAL VARIABLES LIKE 'log_timestamps';

Puede utilizar UTC o la hora del sistema. No aplicamos una diferencia horaria fija sin comprobar la configuración y la zona horaria del equipo.

¿Por qué la hora del registro no coincide con nuestro reloj?

El registro puede utilizar UTC, una hora de referencia mundial. La letra Z al final de la fecha indica que se está utilizando UTC.

En la España peninsular, la hora local está una hora por delante de UTC en invierno y dos horas en verano. Por ejemplo, las 10:15 UTC corresponden a las 12:15 en horario de verano.

Debemos tener en cuenta esta diferencia al buscar un evento por su hora. No significa que el servidor tenga el reloj mal.

🔶 Consultamos desde SQL​

Con el servidor iniciado, podemos intentar consultar los sucesos recientes del registro de errores mediante la tabla performance_schema.error_log.

Esta tabla depende de los componentes de registro habilitados. Si no devuelve filas, consultamos directamente el archivo .err, como hemos explicado antes. Un resultado vacío no significa necesariamente que no se hayan producido sucesos.

SELECT LOGGED, PRIO, ERROR_CODE, SUBSYSTEM, DATA
FROM performance_schema.error_log
ORDER BY LOGGED DESC
LIMIT 10;
en este ejemplo

Mostramos la fecha y hora del suceso (LOGGED), su prioridad (PRIO), el código del mensaje (ERROR_CODE), el componente que lo genera (SUBSYSTEM) y su descripción (DATA).

ORDER BY LOGGED DESC coloca primero los sucesos más recientes y LIMIT 10 muestra como máximo diez filas.

Esta consulta requiere que el servidor esté funcionando. Si MySQL no arranca, consultamos directamente el archivo de errores.

🔶 Ajustamos el detalle cuando lo necesitamos​

La variable log_error_verbosity permite ajustar cuánto detalle recoge el registro de errores. Podemos aumentarlo durante una investigación para disponer de más información y recuperar después el valor anterior.

Con el filtro de registro predeterminado de MySQL, los valores disponibles son:

ValorMensajes incluidos
1Errores.
2Errores y advertencias.
3Errores, advertencias y notas informativas.

Los mensajes de tipo System se mantienen con estos niveles.

En la consola de MySQL, conectados como root, guardamos el valor inicial y aumentamos el detalle:

SET @verbosidad_inicial = @@GLOBAL.log_error_verbosity;
SET GLOBAL log_error_verbosity = 3;
SELECT @@GLOBAL.log_error_verbosity;
en este ejemplo

La primera instrucción guarda el valor anterior en una variable de nuestra sesión. Después establecemos el nivel 3 para el servidor y consultamos el valor efectivo para comprobar el cambio.

Cambiar el nivel no añade información a los mensajes antiguos: afecta a los mensajes nuevos que se generen.

Cuando terminemos la comprobación, recuperamos el valor anterior sin cerrar esta sesión:

SET GLOBAL log_error_verbosity = @verbosidad_inicial;
SELECT @@GLOBAL.log_error_verbosity;
en este ejemplo

Restauramos el valor que tenía el servidor al comenzar y comprobamos que se ha recuperado.

Si necesitamos cerrar la conexión o reiniciar el servidor, anotamos antes el valor inicial en el cuaderno. La variable @verbosidad_inicial pertenece a la sesión y se pierde al desconectarnos.

6️⃣ Interpretamos un fallo de arranque​

Cuando Windows no consigue iniciar el servicio, su aviso puede ser genérico. Consultamos el registro de errores para buscar información concreta. Si no se ha generado, revisamos también el Visor de eventos, la ruta del servicio y los permisos de acceso a sus archivos.

Por ejemplo, una opción mal escrita puede producir mensajes que incluyan:

unknown variable 'max_conections=20'
Aborting

max_conections está mal escrito: falta una n. El primer mensaje explica una causa y el segundo indica que se abandona el arranque.

Seguimos este orden:

  1. Delimitamos el intento de arranque por la fecha y hora.
  2. Leemos los mensajes en orden y localizamos las posibles causas.
  3. Contrastamos el mensaje con el cambio realizado.
  4. Corregimos la configuración o recuperamos la copia anterior.
  5. Iniciamos el servicio y comprobamos que vuelve a responder.

En este ejemplo interpretamos un fragmento de registro: no necesitamos provocar el fallo en nuestra VM.

Relacionamos unknown variable con la opción mal escrita y Aborting con la interrupción del arranque. Para resolverlo, corregiríamos max_conections por max_connections en el archivo de configuración que utiliza el servicio. Después iniciaríamos MySQL y comprobaríamos su estado, el registro y la ejecución de una consulta.

Si realizamos esta prueba en el laboratorio, antes guardamos una copia del archivo de configuración y nos aseguramos de saber cómo recuperarla si el servicio no arranca.

7️⃣ Observamos peticiones con el registro general​

El registro general sirve para observar qué recibe el servidor. Puede crecer rápidamente y recoger información sensible. Lo utilizamos durante una prueba breve con consultas inocuas.

En la consola MySQL, registramos el estado y el destino:

SELECT @@GLOBAL.general_log,
       @@GLOBAL.general_log_file,
       @@GLOBAL.log_output;
en este ejemplo

Antes de cambiar nada, consultamos y anotamos:

  • general_log: si el registro está activado (ON o 1) o desactivado (OFF o 0).
  • general_log_file: la ubicación del archivo donde se escribe cuando el destino incluye FILE.
  • log_output: el destino de los registros general y de consultas lentas.

Estos datos nos permiten decidir si podemos seguir el ejemplo y recuperar después el estado inicial.

El siguiente ejemplo supone que el registro general está desactivado y log_output incluye FILE. Si no se cumple, revisamos primero la configuración. log_output también afecta al registro de consultas lentas.

SET GLOBAL general_log = ON;
SELECT 'PRUEBA_REGISTRO_UT3' AS marca;
SET GLOBAL general_log = OFF;
en este ejemplo

SET GLOBAL general_log = ON activa el registro general. Después enviamos una consulta con el texto PRUEBA_REGISTRO_UT3, que utilizamos como marca para localizarla fácilmente en el archivo.

SET GLOBAL general_log = OFF desactiva el registro al terminar la prueba. En este ejemplo recuperamos así su estado inicial, que era desactivado.

La marca permite comprobar que el servidor ha registrado la instrucción recibida. No estamos creando una tabla ni guardando ese texto en una base de datos.

Dentro de la VM, abrimos con el Bloc de notas el archivo indicado por general_log_file. Si el valor muestra solo un nombre de archivo, lo buscamos dentro de la carpeta indicada por datadir.

Pulsamos Ctrl + F y buscamos PRUEBA_REGISTRO_UT3. Localizamos la entrada correspondiente a nuestra consulta y observamos su hora y su identificador de conexión.

Si el archivo ya estaba abierto antes de la prueba, lo cerramos y volvemos a abrirlo para ver las nuevas entradas.

Para observar también una conexión y una desconexión, podemos repetir la prueba abriendo y cerrando un segundo cliente mientras el registro está activado. Después lo desactivamos.

Comprobamos que el registro general vuelve a estar desactivado:

SELECT @@GLOBAL.general_log;

El resultado debe ser 0 (OFF), que era el estado inicial de este ejemplo.

Durante la prueba no cambiamos contraseñas ni ejecutamos consultas con datos personales.

Qué nos dice cada registro

El registro de errores ayuda a explicar lo ocurrido en el servidor. El registro general permite observar las peticiones recibidas, pero una sentencia registrada no demuestra por sí sola que terminara correctamente ni que sus cambios se confirmaran.
