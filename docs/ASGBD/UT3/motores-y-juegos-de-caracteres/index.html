3.4. Motores, juegos de caracteres y cotejamientos

Cuando creamos una tabla o una base de datos sin indicar todas sus características, MySQL utiliza valores por defecto. Elegirlos requiere comprender cómo se almacenan los datos, qué operaciones admite el motor y cómo se representan y comparan los textos.

Dónde trabajamos

Trabajamos dentro de la VM, en la consola de MySQL y conectados como root. Los ejemplos utilizan bases de pruebas independientes. No modificamos las tablas de otras prácticas.

Los comandos de este documento son SQL: no los escribimos en PowerShell ni en el Símbolo del sistema de Windows.

1️⃣ Elegimos el motor de almacenamiento​

El motor de almacenamiento es el componente que gestiona cómo se guardan y recuperan los datos de una tabla. MySQL procesa las instrucciones SQL y delega en el motor las operaciones de almacenamiento.

Cada tabla tiene un motor. Una misma base puede contener tablas con motores diferentes. El motor influye en aspectos como la posibilidad de deshacer modificaciones, proteger relaciones con claves foráneas o recuperarse de una interrupción inesperada.

Consultamos los motores de nuestra instalación:

SHOW ENGINES;
en este ejemplo

Cada fila corresponde a un motor. Engine muestra su nombre y Support indica si está disponible (YES), si es el predeterminado (DEFAULT) o si no está disponible o está deshabilitado (NO o DISABLED).

Transactions indica si admite transacciones, Savepoints si admite puntos de recuperación dentro de ellas y XA si admite transacciones distribuidas. No necesitamos trabajar con XA en esta unidad.

Localizamos InnoDB y comprobamos si figura como DEFAULT.

🔶 Comparamos las opciones principales​

MotorTransaccionesClaves foráneasQué debemos tener en cuenta
InnoDBSí.Sí.Motor general predeterminado de MySQL 8.0. Incluye mecanismos de recuperación tras fallos.
MyISAMNo.No.Podemos encontrarlo en instalaciones heredadas. Sus modificaciones no se deshacen con ROLLBACK.
MEMORYNo.No.Mantiene las filas en memoria. Al reiniciar el servidor, la tabla conserva su definición pero pierde sus filas.
CSVNo.No.Almacena datos en archivos CSV. Tiene limitaciones que lo alejan del uso general.

Existen otros motores para necesidades específicas. No necesitamos aprender sus nombres de memoria: debemos saber comprobar qué ofrecen y justificar la elección.

InnoDB utiliza bloqueos a nivel de fila en muchas operaciones, lo que favorece el trabajo concurrente. Esto no elimina las esperas ni los conflictos: dos sesiones que necesitan modificar los mismos datos pueden bloquearse entre sí.

🔷 Entendemos qué aporta una transacción​

Una transacción agrupa operaciones que deben completarse juntas. Si se confirman, sus cambios quedan guardados. Si se deshacen antes de confirmarse, recuperamos la situación anterior para esos cambios.

Por ejemplo, al trasladar una cantidad entre dos saldos necesitamos descontarla de uno y sumarla al otro. Si solo se completara la primera operación, el resultado sería incoherente.

  • START TRANSACTION inicia una transacción.
  • COMMIT confirma sus cambios.
  • ROLLBACK deshace los cambios de la transacción que los motores transaccionales puedan revertir.

No todas las instrucciones pueden deshacerse. En esta prueba usamos inserciones, sin mezclar dentro de la transacción instrucciones de creación o modificación de estructuras.

2️⃣ Comprobamos la diferencia entre motores​

Creamos una base de pruebas y dos tablas con la misma estructura. Si el nombre ya existe por una ejecución anterior, elegimos otro y lo mantenemos durante todo el ejemplo.

CREATE DATABASE pruebas_motores_ut3;
USE pruebas_motores_ut3;

CREATE TABLE t_innodb (id INT PRIMARY KEY) ENGINE = InnoDB;
CREATE TABLE t_myisam (id INT PRIMARY KEY) ENGINE = MyISAM;
en este ejemplo

USE selecciona la base en la que trabajamos. Ambas tablas tienen una columna entera que es clave primaria. Indicamos ENGINE explícitamente para que la diferencia no dependa del motor predeterminado.

La creación de las tablas queda fuera de la transacción que probaremos después.

Iniciamos una transacción, insertamos una fila en cada tabla e intentamos deshacerla:

START TRANSACTION;
INSERT INTO t_innodb VALUES (1);
INSERT INTO t_myisam VALUES (1);
ROLLBACK;
SHOW WARNINGS;
en este ejemplo

La inserción en InnoDB participa en la transacción y puede deshacerse. La realizada en MyISAM no puede revertirse con ROLLBACK.

Consultamos SHOW WARNINGS inmediatamente después para leer la advertencia sobre los cambios en tablas no transaccionales que no se han podido deshacer.

Comprobamos las filas que han quedado:

SELECT COUNT(*) AS filas_innodb FROM t_innodb;
SELECT COUNT(*) AS filas_myisam FROM t_myisam;

Esperamos 0 en InnoDB y 1 en MyISAM. La misma orden de deshacer no ofrece el mismo resultado en ambos motores. Por eso no basta con que una aplicación envíe ROLLBACK: sus tablas deben admitir transacciones.

🔶 Consultamos el motor efectivo y el predeterminado​

SELECT @@GLOBAL.default_storage_engine AS motor_global,
       @@SESSION.default_storage_engine AS motor_sesion;

SELECT TABLE_NAME, ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'pruebas_motores_ut3'
ORDER BY TABLE_NAME;
en este ejemplo

La primera consulta distingue el valor global del de nuestra sesión. Al crear una tabla sin ENGINE, se utiliza el predeterminado de la sesión.

La segunda consulta comprueba el motor de las tablas existentes. Cambiar un valor predeterminado no convierte las tablas que ya hemos creado.

Para convertir una tabla existente indicamos el cambio explícitamente:

ALTER TABLE pruebas_motores_ut3.t_myisam ENGINE = InnoDB;

Esta operación reconstruye la tabla. En una instalación real debemos valorar su tamaño, las restricciones y el impacto antes de ejecutarla. Volvemos a consultar el diccionario para comprobar la conversión. El nombre t_myisam no cambia automáticamente, aunque su motor ya sea InnoDB.

Justificamos la elección

Elegimos InnoDB cuando necesitamos transacciones, claves foráneas y un motor general con recuperación tras fallos. Si ya es el predeterminado, comprobamos el valor sin cambiarlo innecesariamente.

Elegir otro motor requiere una necesidad concreta y conocer las garantías que dejamos de tener.

3️⃣ Diferenciamos juego de caracteres y cotejamiento​

El juego de caracteres determina qué caracteres podemos representar y cómo se codifican. El cotejamiento establece las reglas para comparar y ordenar esos textos.

Son decisiones relacionadas, pero distintas. Poder guardar López no determina si una búsqueda de lopez debe encontrarlo. La primera cuestión depende de la representación del texto y la segunda, de las reglas de comparación.

🔶 Utilizamos utf8mb4​

SHOW CHARACTER SET LIKE 'utf8%';
en este ejemplo

Mostramos los juegos cuyo nombre comienza por utf8. La columna Maxlen indica el número máximo de bytes que puede ocupar un carácter en ese juego, no lo que ocupa necesariamente cada carácter.

NombreQué debemos saber en MySQL 8.0
utf8mb4Representa Unicode con entre 1 y 4 bytes por carácter. Es la opción que utilizamos para textos nuevos.
utf8mb3Solo representa parte de Unicode, con un máximo de 3 bytes. Está obsoleto.
utf8Es un alias de utf8mb3 en esta versión. No debemos confundirlo con utf8mb4.

🔷 Distinguimos caracteres y bytes​

Usamos un ejemplo que no depende de escribir tildes correctamente en el terminal:

SELECT CHAR_LENGTH(CONVERT(0x4CC3B370657A USING utf8mb4)) AS caracteres,
       LENGTH(CONVERT(0x4CC3B370657A USING utf8mb4)) AS bytes;
en este ejemplo

El valor hexadecimal contiene los bytes UTF-8 del texto López. CONVERT(... USING utf8mb4) los interpreta como ese juego de caracteres.

CHAR_LENGTH cuenta caracteres y LENGTH cuenta bytes. El resultado es 5 caracteres y 6 bytes, porque la ó ocupa dos bytes.

La diferencia entre ambos recuentos no demuestra por sí sola que un texto esté bien o mal guardado. Para diagnosticar un problema debemos conocer el texto esperado y revisar la codificación del archivo, del cliente y de la columna.

4️⃣ Elegimos las reglas de comparación​

Consultamos los cotejamientos modernos específicos del español:

SHOW COLLATION LIKE 'utf8mb4_es_0900%';
en este ejemplo

Cada fila es un cotejamiento disponible. No cambiamos la configuración al ejecutar esta consulta: consultamos qué opciones podemos elegir.

En utf8mb4_es_0900_ai_ci, las partes del nombre aportan esta información:

ParteSignificado
utf8mb4Juego de caracteres al que pertenece.
esReglas específicas del español.
0900Reglas basadas en UCA 9.0.0.
aiNo distingue acentos en las comparaciones correspondientes.
ciNo distingue mayúsculas y minúsculas.

Otros nombres incluyen as, que distingue acentos, o cs, que distingue mayúsculas. Estas abreviaturas no sustituyen las reglas del idioma: con el cotejamiento español, ñ sigue siendo distinta de n aunque aparezca ai.

CotejamientoMayúsculasAcentosComparación de n y ñ
utf8mb4_0900_ai_ciNo distingue.No distingue.Las considera equivalentes.
utf8mb4_es_0900_ai_ciNo distingue.No distingue.Las diferencia según las reglas del español.
utf8mb4_es_0900_as_csDistingue.Distingue.Las diferencia.

🔶 Probamos las comparaciones​

Definimos dos textos a partir de sus bytes UTF-8 para evitar depender de la escritura de tildes en la consola:

SET @apellido_tilde = CONVERT(0x4CC3B370657A USING utf8mb4);
SET @apellido_enie = CONVERT(0x4962C3A1C3B1657A USING utf8mb4);
en este ejemplo

La primera variable contiene López y la segunda Ibáñez. Son variables de nuestra sesión, utilizadas únicamente para la demostración. Se pierden al cerrar la conexión.

Comparamos los textos:

SELECT @apellido_tilde COLLATE utf8mb4_es_0900_ai_ci
       = _utf8mb4'lopez' AS coincide_lopez;

SELECT @apellido_enie COLLATE utf8mb4_0900_ai_ci
       = _utf8mb4'ibanez' AS coincide_general;

SELECT @apellido_enie COLLATE utf8mb4_es_0900_ai_ci
       = _utf8mb4'ibanez' AS coincide_espanol;
en este ejemplo

COLLATE elige las reglas de esa comparación. El prefijo _utf8mb4 identifica el juego de caracteres de los literales utilizados.

Esperamos los resultados 1, 1 y 0. La primera comparación ignora mayúsculas y acentos. La segunda también considera equivalentes n y ñ. La tercera aplica las reglas españolas y las diferencia.

No modificamos los textos ni la configuración del servidor por utilizar COLLATE en estas consultas.

Ordenar también depende del cotejamiento

Estas reglas afectan tanto a comparaciones, por ejemplo en WHERE, como a la ordenación de columnas de texto con ORDER BY. También influyen en qué valores se consideran iguales al comprobar una restricción de unicidad.

5️⃣ Comprobamos los niveles y la herencia​

El servidor proporciona valores predeterminados para las bases nuevas. Una base proporciona los de sus tablas nuevas y una tabla los de sus columnas de texto nuevas, cuando no indicamos otros explícitamente.

Esta herencia se aplica al crear los objetos. No es una vinculación que actualice automáticamente todos los objetos cuando cambiamos un valor superior.

NivelQué consultamos
Servidor.character_set_server y collation_server.
Base de datos.Valores predeterminados en information_schema.SCHEMATA.
Tabla.Cotejamiento predeterminado en information_schema.TABLES.
Columna de texto.Juego y cotejamiento en information_schema.COLUMNS.

🔶 Creamos objetos con valores heredados y explícitos​

Primero consultamos los valores actuales:

SELECT @@GLOBAL.character_set_server, @@GLOBAL.collation_server,
       @@SESSION.character_set_server, @@SESSION.collation_server;

Creamos dos bases nuevas. Si sus nombres ya existen, elegimos otros para esta prueba:

CREATE DATABASE textos_heredados_ut3;
CREATE DATABASE textos_espanol_ut3
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_es_0900_ai_ci;

SELECT SCHEMA_NAME, DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA
WHERE SCHEMA_NAME IN ('textos_heredados_ut3', 'textos_espanol_ut3');
en este ejemplo

La primera base toma los valores predeterminados aplicables a nuestra sesión. La segunda recibe valores explícitos, aunque coincidan con los predeterminados.

La consulta al diccionario muestra lo que ha quedado definido realmente. Si ambas bases coinciden, no significa que el ejemplo haya fallado: puede que el servidor ya utilizara los valores elegidos.

Creamos una tabla sin indicar juego ni cotejamiento y consultamos su columna de texto:

CREATE TABLE textos_espanol_ut3.persona (
    id INT PRIMARY KEY,
    apellido VARCHAR(60)
);

SELECT TABLE_NAME, COLUMN_NAME, CHARACTER_SET_NAME, COLLATION_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'textos_espanol_ut3'
  AND TABLE_NAME = 'persona'
  AND COLUMN_NAME = 'apellido';
en este ejemplo

La tabla toma los valores de su base y la columna apellido toma los de la tabla. Comprobamos la columna porque es donde se aplican las reglas a los textos guardados.

🔷 Cambiamos los valores del servidor cuando existe un requisito​

Si necesitamos modificar los predeterminados del servidor, primero registramos los valores globales y sus posibles entradas en performance_schema.persisted_variables, como estudiamos en 3.2. No suponemos que todos los equipos parten de la misma configuración.

Para establecer UTF-8 completo y las reglas españolas sin distinguir mayúsculas ni acentos:

SET PERSIST character_set_server = 'utf8mb4';
SET PERSIST collation_server = 'utf8mb4_es_0900_ai_ci';
en este ejemplo

Aplicamos los valores globales y los guardamos para futuros arranques. Elegimos un cotejamiento que pertenece al juego de caracteres indicado.

Abrimos una conexión nueva antes de crear otra base sin cláusulas explícitas. Así evitamos comprobar el cambio con valores de una sesión anterior. Consultamos el diccionario y, si debemos demostrar la persistencia, verificamos también después de reiniciar.

Cambiar valores predeterminados no convierte los datos existentes

Las bases, tablas y columnas existentes conservan sus propiedades. Cambiar los valores del servidor no cambia automáticamente sus textos ni sus comparaciones.

Del mismo modo, cambiar los predeterminados de una base no convierte las columnas de sus tablas existentes. Una conversión de datos requiere estudiar su impacto y disponer de una copia de seguridad.

Si solo hemos realizado una prueba, recuperamos tanto los valores efectivos como la situación inicial de persistencia para las dos variables, siguiendo 3.2. Comprobamos el resultado desde una conexión nueva.

6️⃣ Revisamos la codificación de la conexión​

Aunque una columna admita utf8mb4, los textos pueden llegar mal interpretados. Entre el archivo o terminal y el servidor interviene también la codificación de la conexión.

SELECT @@SESSION.character_set_client,
       @@SESSION.character_set_connection,
       @@SESSION.character_set_results;
en este ejemplo

character_set_client indica cómo interpreta el servidor los bytes enviados por el cliente. character_set_connection interviene en el tratamiento de los textos de las instrucciones y character_set_results indica la codificación de los resultados enviados al cliente.

Un archivo SQL guardado realmente en UTF-8 puede declarar:

SET NAMES utf8mb4;

Esta instrucción ajusta esas variables de la sesión. No convierte el archivo ni cambia la codificación del terminal. Si los bytes enviados no son UTF-8, declararlos como tales no corrige el problema.

Textos en la consola de Windows

Si aparecen tildes o eñes deformadas, revisamos cómo se guardó el archivo y cómo lo interpreta el cliente. No cambiamos el cotejamiento a ciegas: el cotejamiento decide cómo comparar, pero no repara bytes mal interpretados.

Para las demostraciones anteriores utilizamos valores hexadecimales con bytes conocidos. Para trabajar con archivos, comprobamos que están guardados en UTF-8 y que el cliente utiliza una configuración coherente.

7️⃣ Qué debemos poder justificar​

Ante una configuración debemos explicar por qué el motor ofrece las garantías necesarias, qué caracteres debe admitir el texto y qué diferencias deben tenerse en cuenta al compararlo.

Comprobamos por separado los valores predeterminados, las propiedades de los objetos existentes y la conexión del cliente. Un valor correcto en el servidor no demuestra por sí solo que todas las tablas o todos los textos estén configurados correctamente.

Las bases creadas en este apartado son de pruebas. Si las eliminamos al terminar, comprobamos antes su nombre y que no contienen trabajo que necesitemos conservar. No eliminamos bases de otras prácticas.
