3.7. Clientes e interfaces estándar

Un servidor de bases de datos no se utiliza solo desde una consola. Las personas trabajan con herramientas cliente y las aplicaciones se conectan mediante interfaces de programación. En este apartado configuraremos una herramienta gráfica y conoceremos las interfaces estándar ODBC y JDBC.

1️⃣ Tipos de clientes​

TipoEjemplosQuién lo utiliza
Cliente de consolamysql, mysqladminAdministración y scripts.
Herramienta gráficaMySQL Workbench, DBeaverAdministración, consultas y diseño.
AplicaciónProgramas de gestión, hojas de cálculo, informesUsuarios finales, a través de un conector.

Todos utilizan el mismo protocolo para comunicarse con el servidor. Lo que cambia es cómo se presentan y qué cuenta utilizan.

2️⃣ MySQL Workbench​

MySQL Workbench es la herramienta gráfica oficial de MySQL. Permite ejecutar consultas, administrar el servidor, consultar su estado y diseñar modelos. Se instala en el equipo cliente, no en el servidor.

🔸 Configuramos una conexión​

En la pantalla principal pulsamos + junto a MySQL Connections y completamos:

CampoValor
Connection NameNombre descriptivo de la conexión.
Connection MethodStandard (TCP/IP).
HostnameDirección IP del servidor.
Port3306.
UsernameCuenta autorizada desde este equipo.
PasswordStore in Vault para guardarla cifrada en Windows, o se pedirá al conectar.
Default SchemaBase de datos con la que trabajaremos (opcional).

Pulsamos Test Connection antes de guardar.

[IMAGEN. Ventana «Setup New Connection» de Workbench con Hostname, Port, Username y Default Schema completados.]

[IMAGEN. Mensaje «Successfully made the MySQL connection» de Test Connection, con la información del servidor y la versión.]

Una vez conectados, comprobamos a qué servidor y con qué cuenta:

SELECT @@hostname, VERSION(), CURRENT_USER(), USER();

[IMAGEN. Editor SQL de Workbench con la consulta anterior y su resultado en la parte inferior.]

Workbench y los privilegios

Workbench muestra todas sus secciones (Server Status, Users and Privileges, Options File…), pero solo funcionan las que permiten los privilegios de la cuenta. Con una cuenta limitada, muchas mostrarán errores de acceso. Es el comportamiento esperado.

Workbench abre varias conexiones

Cada pestaña de conexión de Workbench puede mantener más de una conexión con el servidor. Lo tenemos en cuenta al decidir max_connections y al interpretar SHOW PROCESSLIST.

3️⃣ Interfaces estándar: conectores​

Una aplicación no habla directamente con MySQL: utiliza un conector o controlador (driver). Si la aplicación utiliza una interfaz estándar, puede trabajar con diferentes gestores cambiando solo el controlador y los datos de conexión.

InterfazPara qué aplicacionesConector de MySQL
ODBC (Open Database Connectivity)Aplicaciones de Windows y lenguajes como C, C++, PowerShell, Excel, Access…MySQL Connector/ODBC
JDBC (Java Database Connectivity)Aplicaciones Java.MySQL Connector/J

MySQL ofrece también conectores para .NET, Python, Node.js y otros lenguajes. ODBC y JDBC son los dos estándares más extendidos y no dependen de un gestor concreto.

🔸 Cómo funciona ODBC​

ODBC tiene tres piezas:

  1. La aplicación pide datos mediante funciones ODBC estándar.
  2. El administrador de controladores de Windows recibe la petición y la entrega al controlador adecuado.
  3. El controlador de MySQL traduce la petición al protocolo de MySQL y la envía al servidor.

Para no repetir los datos de conexión en cada aplicación, se define un origen de datos (DSN): un nombre que agrupa servidor, puerto, cuenta y base de datos.

Tipo de DSNDisponible para
De usuarioSolo la cuenta de Windows que lo crea.
De sistemaTodas las cuentas del equipo.

🔸 Cómo funciona JDBC​

En JDBC, el controlador es un archivo .jar que la aplicación Java incluye en su classpath. Los datos de conexión se indican en una URL:

jdbc:mysql://192.168.10.128:3306/nombre_base

Un programa mínimo que se conecta y consulta la versión del servidor:

import java.sql.*;

public class PruebaJdbc {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:mysql://192.168.10.128:3306/nombre_base";
        try (Connection c = DriverManager.getConnection(url, "cuenta", "contraseña");
             Statement s = c.createStatement();
             ResultSet r = s.executeQuery("SELECT VERSION(), CURRENT_USER()")) {
            while (r.next()) {
                System.out.println(r.getString(1) + " - " + r.getString(2));
            }
        }
    }
}

Con Java 11 o posterior podemos ejecutarlo sin compilar previamente:

java -cp mysql-connector-j-9.x.x.jar PruebaJdbc.java

El código no contiene nada específico de MySQL salvo la URL: con otro controlador y otra URL, funcionaría con otro gestor.

4️⃣ Prueba guiada: conexión mediante ODBC​

🔸 1. Instalamos el controlador​

Descargamos MySQL Connector/ODBC de 64 bits desde la web oficial de MySQL e instalamos el MSI en el equipo cliente. El instalador puede requerir el paquete Microsoft Visual C++ Redistributable.

🔸 2. Comprobamos el controlador​

Abrimos Orígenes de datos ODBC (64 bits) (odbcad32.exe) y, en la pestaña Controladores, comprobamos que aparecen dos versiones:

  • MySQL ODBC … Unicode Driver: la utilizaremos, porque transmite correctamente cualquier carácter de utf8mb4.
  • MySQL ODBC … ANSI Driver: para aplicaciones antiguas que no admiten Unicode.

[IMAGEN. Administrador de orígenes de datos ODBC (64 bits), pestaña Controladores, con los controladores MySQL ODBC Unicode y ANSI.]

🔸 3. Creamos el DSN​

En la pestaña DSN de sistema, pulsamos Agregar, elegimos el controlador Unicode y completamos:

CampoValor
Data Source NameNombre del origen, sin espacios.
TCP/IP ServerDirección IP del servidor.
Port3306.
User / PasswordCuenta autorizada desde este equipo.
DatabaseBase de datos. Se despliega si la conexión funciona.

Pulsamos Test: debe mostrar Connection successful.

[IMAGEN. Ventana de configuración del DSN con MySQL ODBC Unicode Driver, servidor, puerto, usuario y base de datos completados, y el mensaje Connection successful.]

🔸 4. Una aplicación utiliza el DSN​

Cualquier aplicación compatible con ODBC puede utilizar ahora el origen de datos. Lo comprobamos con PowerShell, que incluye soporte ODBC:

$conexion = New-Object System.Data.Odbc.OdbcConnection("DSN=NombreDSN;PWD=contraseña")
$conexion.Open()
$orden = $conexion.CreateCommand()
$orden.CommandText = "SELECT @@hostname, VERSION(), CURRENT_USER()"
$lector = $orden.ExecuteReader()
while ($lector.Read()) { "{0} | {1} | {2}" -f $lector[0], $lector[1], $lector[2] }
$conexion.Close()

Si el DSN no guarda la contraseña, la indicamos en la cadena con PWD=. No dejamos contraseñas reales escritas en scripts que vayamos a compartir.

[IMAGEN. Ventana de PowerShell con el resultado de la consulta mediante ODBC: nombre del servidor, versión y cuenta.]

Comprobamos también los textos

Si consultamos una columna con tildes o eñes y aparecen correctamente, la cadena completa funciona: datos guardados en utf8mb4, controlador Unicode y aplicación. Si aparecen deformados, revisamos el controlador elegido.

Idea clave

La aplicación no sabe que al otro lado hay MySQL: solo conoce el nombre del origen de datos. Si mañana cambiamos de servidor, actualizamos el DSN y la aplicación sigue funcionando.
