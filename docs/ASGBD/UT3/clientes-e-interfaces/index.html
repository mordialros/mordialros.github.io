3.7. Clientes e interfaces estándar

Podemos acceder a un mismo servidor mediante una consola, una herramienta gráfica o una aplicación. Cambia la forma de trabajar del cliente, pero el servidor sigue comprobando la cuenta, su origen y los permisos de cada operación.

En este apartado configuramos una herramienta gráfica y probamos una interfaz estándar de acceso a datos. Instalar un cliente no implica instalar otro servidor MySQL.

Dónde trabajamos

El servidor está en la VM, que debe permanecer encendida con MySQL iniciado. Instalamos y utilizamos los clientes y el controlador ODBC en el anfitrión.

Partimos de la conectividad y de la cuenta sin privilegios administrativos comprobadas en 3.6. Utilizamos esa cuenta, sin crear otra innecesariamente. Los nombres y direcciones de los ejemplos se sustituyen por los del laboratorio.

1️⃣ Distinguimos herramienta, conexión y controlador​

ElementoQué representa
Herramienta cliente.Programa que utilizamos, como la consola mysql o MySQL Workbench.
Configuración de conexión.Datos guardados para localizar el servidor y presentar una cuenta. No es una sesión abierta por sí misma.
Conexión activa.Sesión que se establece con el servidor al utilizar esos datos y autenticarnos.
Controlador o conector.Software que permite a una aplicación comunicarse con el gestor mediante una interfaz determinada.

Guardar una conexión en Workbench no crea una cuenta en el servidor. De igual modo, cambiar el nombre de esa conexión no cambia el nombre del usuario MySQL.

Una aplicación puede mantener varias conexiones activas. Lo tenemos en cuenta al observar SHOW PROCESSLIST o al justificar max_connections.

2️⃣ Configuramos MySQL Workbench en el anfitrión​

Workbench permite ejecutar consultas, explorar objetos y realizar tareas administrativas cuando la cuenta dispone de los privilegios necesarios. Lo utilizamos como herramienta cliente del servidor de la VM.

Si ya tenemos configurada y comprobada esa conexión, revisamos sus datos en lugar de duplicarla.

🔶 Creamos la configuración de conexión​

En la pantalla principal de Workbench pulsamos + junto a MySQL Connections.

CampoQué indicamos
Connection Name.Nombre descriptivo, como MySQL VM - UT3. Solo identifica esta configuración en el cliente.
Connection Method.Standard (TCP/IP) para la conexión directa de este laboratorio.
Hostname.IPv4 de la VM, no la IP de VMnet8 del anfitrión.
Port.Puerto del protocolo clásico consultado en el servidor, normalmente 3306.
Username.Cuenta autorizada desde el anfitrión, como la que preparamos en 3.6.
Password.Podemos introducirla cuando se solicite. No necesitamos guardarla para la demostración.
Default Schema.Opcional. Lo dejamos vacío si la cuenta solo se utiliza para identificar la conexión.

Por ejemplo, con las direcciones ficticias de 3.6, el destino sería 192.168.10.128. El origen autorizado de la cuenta seguiría siendo 192.168.10.1. No intercambiamos ambas direcciones.

Pulsamos Test Connection e introducimos la contraseña de la cuenta indicada. Si la prueba funciona, guardamos la configuración y la abrimos desde la pantalla principal.

🔷 Ejecutamos e interpretamos una consulta​

En una pestaña del editor SQL escribimos:

SELECT VERSION(), @@hostname, @@port,
       USER(), CURRENT_USER(), CONNECTION_ID();

Seleccionamos la consulta y pulsamos el botón de ejecución de la selección. También podemos usar Ctrl + Intro para ejecutar la instrucción en la que está el cursor. Leemos el resultado en la cuadrícula inferior.

en este ejemplo

La versión, el nombre y el puerto ayudan a identificar el servidor. USER() muestra cómo nos presentamos y el origen observado. CURRENT_USER() identifica la cuenta que MySQL ha seleccionado para autenticar.

CONNECTION_ID() permite relacionar esta sesión con las que observamos en el servidor. Reutilizamos la captura de identificación de 3.6: no necesitamos documentar otra vez el mismo resultado.

Si la herramienta permite abrir el editor pero no una sección administrativa, revisamos los privilegios de la cuenta. La presencia de un botón no concede permiso para utilizar su función.

🔶 Comprobamos el cifrado de la sesión​

Desde la conexión de Workbench podemos consultar:

SHOW SESSION STATUS LIKE 'Ssl_cipher';
en este ejemplo

TLS es el mecanismo que cifra la comunicación entre cliente y servidor. Un certificado permite al cliente comprobar la identidad del servidor cuando se configura esa verificación. Un valor de cifrado no vacío indica que esa sesión utiliza TLS. No demuestra por sí solo que el cliente haya verificado correctamente la identidad del servidor mediante un certificado de confianza.

No confundimos autenticación, permisos, cifrado y validación del certificado: responden a cuestiones distintas.

En este laboratorio observamos la configuración real antes de modificarla. No desactivamos el cifrado ni la validación de certificados como respuesta automática a cualquier error de conexión.

3️⃣ Entendemos para qué sirven ODBC y JDBC​

Las herramientas de consulta están pensadas para que una persona trabaje directamente con el servidor. Las aplicaciones necesitan además una forma de abrir conexiones, enviar órdenes y leer resultados desde su código.

Una interfaz estándar define operaciones comunes. El controlador del gestor implementa esa interfaz y se comunica con el servidor.

InterfazEntorno habitualControlador de MySQL
ODBC, Open Database Connectivity.Aplicaciones y herramientas de distintos lenguajes y sistemas. En Windows se utiliza, por ejemplo, para integrar herramientas de datos.MySQL Connector/ODBC.
JDBC, Java Database Connectivity.Aplicaciones Java.MySQL Connector/J.

Una aplicación que usa ODBC no necesita conocer todos los detalles del protocolo de MySQL, pero sigue dependiendo de sus consultas, tipos de datos y configuración. Cambiar el controlador no garantiza que todo el programa funcione sin adaptar nada con otro gestor.

🔶 Seguimos una petición ODBC​

En Windows intervienen la aplicación, el administrador de controladores ODBC y el controlador del gestor. La aplicación utiliza la interfaz ODBC, el administrador selecciona el controlador adecuado y este se comunica con MySQL.

Un DSN, nombre de origen de datos, guarda una configuración que la aplicación puede identificar por un nombre. Puede incluir servidor, puerto, usuario y base predeterminada. No es otra base de datos ni una cuenta del servidor.

Tipo de DSNAlcance
De usuario.Lo utiliza la cuenta de Windows que lo crea. Es suficiente para nuestra prueba personal.
De sistema.Puede ser utilizado por otras cuentas o servicios del equipo, con los permisos correspondientes. Crearlo requiere normalmente permisos de administrador.

Un DSN de sistema no concede a todas las personas permiso sobre MySQL. Cada conexión sigue necesitando autenticarse ante el servidor.

🔷 Reconocemos una conexión JDBC​

En Java, la aplicación incluye el controlador Connector/J y utiliza las operaciones JDBC. Una URL puede tener esta forma:

jdbc:mysql://192.168.10.128:3306/base_pruebas

El prefijo identifica JDBC y MySQL. Después aparecen el servidor, el puerto y la base solicitada. El usuario y la contraseña se proporcionan de forma separada y segura según la aplicación.

En esta unidad reconocemos su función y su diferencia con ODBC. No necesitamos preparar un proyecto Java para demostrar ambas interfaces: realizamos la prueba práctica con ODBC.

4️⃣ Preparamos ODBC en el anfitrión​

🔶 Comprobamos la arquitectura del cliente​

La arquitectura del proceso cliente y del controlador ODBC debe coincidir: 32 bits con 32 bits o 64 bits con 64 bits. No elegimos solo por la arquitectura del servidor ni suponemos que todas las aplicaciones de un Windows de 64 bits sean también de 64 bits.

Para esta demostración utilizamos PowerShell de 64 bits. En PowerShell del anfitrión ejecutamos:

[Environment]::Is64BitProcess

True indica que ese proceso es de 64 bits. El controlador que utilice también debe serlo.

🔷 Instalamos o comprobamos el controlador​

En el anfitrión, comprobamos primero si MySQL Connector/ODBC ya está instalado. Si no lo está, descargamos de la web oficial una versión compatible con el servidor y el sistema del laboratorio, con arquitectura de 64 bits para esta prueba.

Instalamos el paquete y los requisitos que indique su documentación. No instalamos otro servidor MySQL. Si necesitamos descargarlo, podemos hacerlo antes de la sesión y conservar el instalador para evitar descargas repetidas.

Abrimos Orígenes de datos ODBC (64 bits) desde Inicio y consultamos Controladores. Seleccionamos el controlador de MySQL con soporte Unicode disponible en la versión instalada. Algunos paquetes ofrecen controladores Unicode y ANSI separados y otros pueden presentar nombres diferentes: comprobamos el paquete real.

Dos administradores ODBC en Windows de 64 bits

El administrador de 64 bits se encuentra en C:\Windows\System32\odbcad32.exe. El de 32 bits está en C:\Windows\SysWOW64\odbcad32.exe.

Aunque los nombres de las carpetas resulten confusos, comprobamos el título de la herramienta y la arquitectura del proceso que va a utilizar el controlador.

🔶 Creamos un DSN de usuario​

En Orígenes de datos ODBC (64 bits) → DSN de usuario → Agregar, elegimos el controlador de MySQL adecuado.

CampoValor para la prueba
Nombre del origen, Data Source Name.MySQL_VM_UT3.
Servidor TCP/IP.IPv4 de la VM.
Puerto.El puerto clásico utilizado, normalmente 3306.
Usuario.La cuenta limitada autorizada desde el anfitrión.
Contraseña.La de esa cuenta, cuando sea necesaria para probar. Evitamos guardarla en el DSN.
Base de datos.Vacía para consultar la identificación. Si la herramienta exige una, utilizamos una base accesible para la cuenta.

Pulsamos Test. Una prueba correcta demuestra que ese controlador puede establecer la conexión con los datos indicados. Todavía nos falta utilizarla desde otra aplicación.

Guardamos el DSN sin una contraseña persistida si el controlador permite separarla. Si el formulario necesita la contraseña para probar, la retiramos antes de guardar y la proporcionamos al utilizar el DSN. No incluimos claves reales en capturas.

5️⃣ Utilizamos el DSN desde PowerShell​

En PowerShell de 64 bits del anfitrión, abrimos una conexión mediante ODBC con la cuenta laboratorio preparada en 3.6.

Código facilitado para una prueba guiada

No necesitamos saber programar en PowerShell para realizar esta comprobación. Utilizamos los bloques facilitados y relacionamos cada parte con su función: pedir credenciales, preparar la conexión, enviar una consulta, leer el resultado y cerrar los recursos.

Las variables que comienzan por $ guardan información u objetos durante esta sesión de PowerShell. Los métodos, como Open() o Dispose(), realizan operaciones sobre esos objetos. No son instrucciones SQL.

🔶 Solicitamos las credenciales sin escribir la clave en el código​

$claveMySql = Read-Host 'Contraseña de laboratorio en MySQL' -AsSecureString
$credencialMySql = New-Object System.Management.Automation.PSCredential ('laboratorio', $claveMySql)
$cadenaOdbc = New-Object System.Data.Odbc.OdbcConnectionStringBuilder
$cadenaOdbc['DSN'] = 'MySQL_VM_UT3'
$cadenaOdbc['UID'] = $credencialMySql.UserName
$cadenaOdbc['PWD'] = $credencialMySql.GetNetworkCredential().Password
$conexionOdbc = New-Object System.Data.Odbc.OdbcConnection
$conexionOdbc.ConnectionString = $cadenaOdbc.ConnectionString
en este ejemplo

Utilizamos laboratorio como nombre de ejemplo: lo sustituimos si nuestra cuenta autorizada tiene otro nombre.

Read-Host solicita la contraseña en la propia consola. Escribimos la contraseña de esa cuenta de MySQL, no la de root ni la de Windows, y pulsamos Intro. -AsSecureString evita mostrarla en texto visible y la guarda como un objeto protegido en $claveMySql.

La segunda instrucción reúne el usuario y la contraseña en $credencialMySql. No muestra ningún resultado: es normal que vuelva el indicador de PowerShell. No escribimos la contraseña real dentro del script.

El constructor reúne el nombre del DSN y las credenciales para abrir la conexión. No imprimimos $cadenaOdbc ni la cadena completa: contienen la contraseña durante su uso en memoria.

🔷 Consultamos y cerramos los recursos​

$ordenOdbc = $null
$lectorOdbc = $null
try {
    $conexionOdbc.Open()
    $ordenOdbc = $conexionOdbc.CreateCommand()
    $ordenOdbc.CommandText = 'SELECT VERSION(), CURRENT_USER(), @@port'
    $lectorOdbc = $ordenOdbc.ExecuteReader()
    while ($lectorOdbc.Read()) {
        '{0} | {1} | {2}' -f $lectorOdbc[0], $lectorOdbc[1], $lectorOdbc[2]
    }
}
finally {
    if ($null -ne $lectorOdbc) { $lectorOdbc.Dispose() }
    if ($null -ne $ordenOdbc) { $ordenOdbc.Dispose() }
    $conexionOdbc.Dispose()
    $cadenaOdbc.Clear()
    Remove-Variable credencialMySql, claveMySql -ErrorAction SilentlyContinue
}
en este ejemplo

Open() establece la conexión. La orden contiene una consulta SQL y ExecuteReader() permite leer sus resultados. El bucle muestra versión, cuenta aceptada y puerto.

Open() no muestra un mensaje de éxito: si no aparece un error, continuamos con la consulta. La línea de resultado muestra la versión del servidor, la cuenta utilizada y el puerto.

try agrupa el intento de conexión y consulta. while recorre las filas del resultado e if comprueba si existe un recurso antes de liberarlo. finally libera los recursos aunque se produzca un error y elimina las variables de credenciales que hemos creado. Cerrar la aplicación cliente no equivale a detener el servidor, pero sí debemos cerrar las conexiones que dejamos de utilizar.

Este código es una demostración de uso del controlador, no un contenido que debamos memorizar línea por línea. Lo importante es reconocer qué aplicación utiliza el DSN, qué controlador interviene y qué servidor responde.

Si la VM se suspende o la conexión deja de estar disponible

La VM debe permanecer encendida y MySQL iniciado durante toda la prueba. Si la VM se suspende, reinicia o pierde la conectividad, una conexión abierta puede dejar de funcionar. Limpiar la pantalla con Clear-Host no recupera la conexión ni borra las variables.

Si estamos ejecutando las instrucciones por separado y todavía no hemos liberado los recursos con Dispose(), podemos cerrar y volver a abrir la conexión:

$conexionOdbc.Close()
$conexionOdbc.Open()

Después creamos de nuevo la orden y el lector y ejecutamos la consulta. Si Open() falla, revisamos el mensaje antes de continuar. Un error de autenticación exige comprobar la cuenta y su contraseña.

Si hemos ejecutado el bloque completo con finally, la conexión ya se ha liberado y las credenciales se han eliminado. En ese caso repetimos los dos bloques de este apartado, empezando por introducir la contraseña.

🔶 Comprobamos los textos cuando exista una base accesible​

Si la cuenta ya dispone de permiso de lectura sobre una tabla con textos conocidos, podemos consultar una columna con tildes y eñes mediante esa conexión. Contrastamos el resultado con el texto esperado.

Si no tiene ese permiso, no concedemos permisos administrativos para completar la prueba. La identificación anterior basta para comprobar la conexión y dejamos la consulta de datos para cuando estén preparados sus permisos.

El controlador Unicode no repara datos que ya se guardaron incorrectamente. Si aparece texto deformado, revisamos los datos almacenados, la codificación de la conexión y la presentación del resultado, como estudiamos en 3.4.

6️⃣ Diagnosticamos los problemas del cliente​

SíntomaQué revisamos
mysql no se reconoce en Windows.Ruta al ejecutable del cliente o configuración de PATH. No implica que el servidor esté detenido.
No aparece el controlador en ODBC.Instalación y coincidencia de arquitectura entre herramienta y controlador.
La aplicación no encuentra el DSN.Nombre exacto, cuenta de Windows que lo creó y arquitectura del proceso.
Error de autenticación.Cuenta, origen permitido, contraseña y compatibilidad del cliente.
Workbench conecta pero una aplicación ODBC no.Sus configuraciones pueden diferir. Contrastamos destino, puerto, controlador y credenciales.
Conecta pero no puede leer una tabla.Permisos de la cuenta y nombre de la base o tabla.
Texto incorrecto.Datos originales, codificación de la conexión y tratamiento del texto en la aplicación.

Las interfaces no eliminan los requisitos de red ni los permisos. Diagnosticamos con el mensaje concreto y cambiamos un elemento cada vez.

7️⃣ Qué debemos poder explicar​

Al terminar distinguimos el servidor, la herramienta cliente, la cuenta y las conexiones activas. Sabemos configurar un cliente gráfico, identificar el destino real y explicar para qué sirve un controlador estándar.

La prueba ODBC completa el recorrido: una aplicación utiliza un DSN y un controlador para consultar el mismo servidor de la VM. Cambiar los datos del DSN puede evitar modificar esos datos en la aplicación, pero no garantiza compatibilidad automática de todas sus consultas con otro gestor.
