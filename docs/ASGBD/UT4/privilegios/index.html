4.2. Gestión de privilegios en MySQL

En el 4.1 aprendimos a crear y administrar cuentas de MySQL. Ahora debemos resolver la siguiente cuestión: una cuenta puede conectarse al servidor, pero ¿qué operaciones debe poder realizar sobre los datos?

En una empresa de soporte informático hay necesidades distintas: consultar incidencias, registrar nuevas incidencias o actualizar su estado. Nuestra tarea como administradores consiste en conceder los permisos adecuados y comprobar que se respetan.

Dónde trabajamos

  • VM con Windows 11 Pro: utilizamos la consola de MySQL para administrar el servidor mediante SQL. En el apartado 4.6 utilizaremos también MySQL Workbench, instalado en la VM, para administrar cuentas y privilegios desde su interfaz gráfica.

  • Anfitrión: mantenemos Workbench para comprobar conexiones remotas con cuentas limitadas, como en la UT3.

  • Base de datos: soporte_tic, preparada al inicio de la unidad.

Los comandos que comienzan con mysql -u se ejecutan en CMD de Windows. Las sentencias SQL se ejecutan dentro de MySQL, cuando aparece mysql>.

1️⃣ ¿Qué son los privilegios?​

Los privilegios son permisos que determinan las operaciones que puede realizar una cuenta sobre las bases de datos y sus objetos, como tablas y vistas.

PrivilegioPermiteEjemplo en soporte_tic
SELECTConsultar datos.Ver incidencias registradas.
INSERTAñadir registros.Registrar una incidencia.
UPDATEModificar registros.Cambiar el estado de una incidencia.
DELETEEliminar registros.Borrar una incidencia.

🔶 Otros privilegios del SGBD​

Además de consultar y modificar datos, MySQL dispone de privilegios para administrar la estructura de las bases de datos y determinadas funciones del servidor.

Tipo de privilegioEjemplosPara qué sirve
DatosSELECT, INSERT, UPDATE, DELETEConsultar y modificar registros.
EstructuraCREATE, ALTER, DROP, CREATE VIEWCrear, modificar o eliminar objetos de la base de datos.
AdministraciónCREATE USER, PROCESS, RELOADGestionar cuentas y realizar determinadas tareas de administración del servidor.

Podemos consultar los privilegios reconocidos por MySQL mediante:

SHOW PRIVILEGES;

Esta instrucción muestra los privilegios disponibles y una breve descripción de su finalidad. No muestra los privilegios concedidos a una cuenta concreta; para eso utilizamos SHOW GRANTS.

Principio de mínimo privilegio

Cada cuenta debe disponer solo de los permisos que necesita para realizar su trabajo. Si una cuenta únicamente consulta incidencias, no debemos concederle permisos para modificarlas ni eliminarlas.

Este principio reduce el riesgo de errores y accesos indebidos: si alguien utiliza una cuenta por equivocación o sin autorización, las operaciones que podrá realizar estarán limitadas por sus privilegios.

🔶 ¿Sobre qué objetos podemos conceder permisos?​

El alcance de los privilegios puede ser diferente:

ÁmbitoSe indica conQué abarca
Servidor*.*Ámbito global del servidor, según el privilegio.
Base de datossoporte_tic.*Objetos aplicables de esa base de datos.
Tablasoporte_tic.incidenciasSolo la tabla incidencias.

En esta unidad concederemos permisos sobre tablas, para ajustar el acceso a las necesidades de cada cuenta.

2️⃣ Concedemos permisos con GRANT​

GRANT permite conceder uno o varios privilegios a una cuenta de MySQL. Su sintaxis general es:

GRANT privilegio [, privilegio ...]
ON base_datos.objeto
TO 'usuario'@'host';
  • privilegio: operación autorizada (SELECT, INSERT, UPDATE, DELETE, etc.). Podemos indicar varias separadas por comas.
  • base_datos.objeto: objeto sobre el que se aplican los permisos, según los ámbitos explicados anteriormente.
  • 'usuario'@'host': cuenta a la que se conceden.

Vamos a preparar tres cuentas con necesidades distintas. En todos los ejemplos seguiremos los mismos pasos: 1. Crear la cuenta → 2. Conceder privilegios → 3. Consultar e interpretar los privilegios.

Antes de comenzar

Todas las instrucciones de este apartado se ejecutan en la consola administrativa de MySQL de la VM, no en CMD. Las cuentas se conectarán localmente (localhost) y las contraseñas indicadas son marcadores que debes sustituir por claves de prueba propias.

🔶 Cuenta para consultar incidencias​

Una persona necesita consultar las incidencias, pero no modificarlas.

Paso 1. Creamos la cuenta

CREATE USER 'consulta_tic'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_CLAVE_PROPIA';

Paso 2. Concedemos los privilegios

Permitimos únicamente la lectura de la tabla incidencias:

GRANT SELECT ON soporte_tic.incidencias
TO 'consulta_tic'@'localhost';

Paso 3. Consultamos los privilegios

SHOW GRANTS FOR 'consulta_tic'@'localhost';

MySQL muestra:

GRANT USAGE ON *.* TO `consulta_tic`@`localhost`
GRANT SELECT ON `soporte_tic`.`incidencias` TO `consulta_tic`@`localhost`
en este ejemplo

La primera línea contiene USAGE ON *.*. Aunque *.* representa el ámbito global, USAGE no concede permisos para consultar o modificar datos: indica que la cuenta no tiene privilegios globales.

La segunda línea concede SELECT sobre soporte_tic.incidencias. Por tanto, consulta_tic puede consultar esa tabla, pero no insertar, modificar ni eliminar sus registros.

🔶 Cuenta para registrar incidencias​

Imaginemos una aplicación web donde los empleados comunican averías. Los empleados utilizan la aplicación, pero no se conectan directamente a MySQL. La aplicación utiliza una cuenta de servicio.

En la UT3 vimos que las aplicaciones pueden utilizar conectores como ODBC o JDBC para comunicarse con el SGBD. El conector establece la comunicación; MySQL comprueba qué operaciones puede realizar la cuenta. En nuestro laboratorio representaremos esa conexión mediante una cuenta local, sin desarrollar la aplicación.

Paso 1. Creamos la cuenta

CREATE USER 'registro_tic'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_CLAVE_PROPIA';

Paso 2. Concedemos los privilegios

La aplicación necesita consultar y registrar incidencias, pero no modificar ni eliminar las existentes:

GRANT SELECT, INSERT ON soporte_tic.incidencias
TO 'registro_tic'@'localhost';

Paso 3. Consultamos los privilegios

SHOW GRANTS FOR 'registro_tic'@'localhost';

MySQL muestra:

GRANT USAGE ON *.* TO `registro_tic`@`localhost`
GRANT SELECT, INSERT ON `soporte_tic`.`incidencias` TO `registro_tic`@`localhost`
en este ejemplo

La segunda línea indica que registro_tic puede consultar (SELECT) e insertar (INSERT) incidencias. No tiene concedidos UPDATE ni DELETE, por lo que no podrá modificar ni eliminar registros existentes.

Una simplificación para aprender

En una aplicación real, la cuenta de servicio tendrá los permisos que requieran sus operaciones y las tablas utilizadas. Aquí limitamos los permisos a incidencias para practicar el control de acceso.

🔶 Cuenta para modificar incidencias​

Una herramienta interna de gestión necesita consultar las incidencias y actualizar su estado, pero no registrar nuevas incidencias ni eliminar las existentes.

Paso 1. Creamos la cuenta

CREATE USER 'gestion_tic'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_CLAVE_PROPIA';

Paso 2. Concedemos los privilegios

GRANT SELECT, UPDATE ON soporte_tic.incidencias
TO 'gestion_tic'@'localhost';

Paso 3. Consultamos los privilegios

SHOW GRANTS FOR 'gestion_tic'@'localhost';

MySQL muestra:

GRANT USAGE ON *.* TO `gestion_tic`@`localhost`
GRANT SELECT, UPDATE ON `soporte_tic`.`incidencias` TO `gestion_tic`@`localhost`
en este ejemplo

La cuenta puede consultar (SELECT) y modificar (UPDATE) los registros de incidencias. Como no se han concedido INSERT ni DELETE, no puede añadir ni eliminar incidencias.

3️⃣ Comprobamos las operaciones permitidas y denegadas​

SHOW GRANTS permite conocer los privilegios concedidos, pero también debemos comprobarlos con una sesión real. Para cada cuenta seguiremos tres pasos: conectarnos, realizar una operación permitida e intentar una operación denegada.

Las conexiones se inician desde CMD de la VM; una vez aparezca mysql>, ejecutamos las consultas SQL. Antes de probar otra cuenta, cerramos la sesión actual y volvemos a CMD.

🔶 Cuenta de consulta: SELECT permitido y UPDATE denegado​

Paso 1. Nos conectamos con la cuenta

Desde CMD de la VM:

mysql --default-character-set=utf8mb4 -u consulta_tic -p

Paso 2. Comprobamos una operación permitida

Dentro de MySQL, consultamos una incidencia:

SELECT id_incidencia, titulo, estado
FROM soporte_tic.incidencias
WHERE id_incidencia = 1;

MySQL muestra:

+---------------+-----------------------------+---------+
| id_incidencia | titulo                      | estado  |
+---------------+-----------------------------+---------+
|             1 | No se puede iniciar sesión  | abierta |
+---------------+-----------------------------+---------+
1 row in set

Paso 3. Comprobamos una operación denegada

Intentamos modificar la misma incidencia:

UPDATE soporte_tic.incidencias
SET estado = 'resuelta'
WHERE id_incidencia = 1;

MySQL devuelve:

ERROR 1142 (42000): UPDATE command denied to user 'consulta_tic'@'localhost' for table 'incidencias'
en este ejemplo

La consulta funciona porque la cuenta tiene SELECT. El error 1142 confirma que MySQL rechaza UPDATE porque no se ha concedido ese privilegio. La incidencia conserva su estado original.

🔶 Cuenta de registro: INSERT permitido y DELETE denegado​

Paso 1. Nos conectamos con la cuenta

Cerramos la sesión anterior y, desde CMD de la VM, ejecutamos:

mysql --default-character-set=utf8mb4 -u registro_tic -p

Paso 2. Comprobamos una operación permitida

Registramos una incidencia de prueba dentro de una transacción para poder deshacerla:

START TRANSACTION;

INSERT INTO soporte_tic.incidencias
(titulo, descripcion, estado, prioridad, fecha_apertura, id_usuario)
VALUES
('Incidencia de prueba', 'Registro temporal para comprobar INSERT',
 'abierta', 'baja', CURDATE(), 1);

ROLLBACK;

Resultado esperado: el INSERT muestra Query OK, 1 row affected. ROLLBACK deshace la inserción y mantiene los datos de partida.

Paso 3. Comprobamos una operación denegada

DELETE FROM soporte_tic.incidencias
WHERE id_incidencia = 1;

Resultado esperado: MySQL rechaza la operación con un error de privilegios DELETE (habitualmente ERROR 1142).

en este ejemplo

registro_tic puede añadir incidencias porque tiene INSERT, pero no puede eliminarlas porque no dispone de DELETE. La comprobación muestra que los permisos concedidos se aplican también a las operaciones que intenta ejecutar una aplicación.

🔶 Cuenta de gestión: UPDATE permitido e INSERT denegado​

Paso 1. Nos conectamos con la cuenta

Cerramos la sesión anterior y, desde CMD de la VM, ejecutamos:

mysql --default-character-set=utf8mb4 -u gestion_tic -p

Paso 2. Comprobamos una operación permitida

Modificamos temporalmente el estado de una incidencia:

START TRANSACTION;

UPDATE soporte_tic.incidencias
SET estado = 'en_proceso'
WHERE id_incidencia = 1;

ROLLBACK;

Resultado esperado: el UPDATE se ejecuta correctamente y ROLLBACK deshace el cambio.

Paso 3. Comprobamos una operación denegada

Intentamos registrar una incidencia:

INSERT INTO soporte_tic.incidencias
(titulo, descripcion, fecha_apertura, id_usuario)
VALUES
('Otra incidencia', 'Intento de inserción sin permiso', CURDATE(), 1);

Resultado esperado: MySQL rechaza la operación porque la cuenta no dispone de INSERT. No se añade ningún registro.

en este ejemplo

gestion_tic tiene SELECT y UPDATE, por lo que puede consultar y modificar las incidencias. No tiene INSERT, de modo que MySQL impide crear nuevos registros.

Comprobaciones seguras

No realices las pruebas de operaciones denegadas con root: una cuenta administrativa podría ejecutarlas. Para las pruebas de modificación autorizada, utilizamos START TRANSACTION y ROLLBACK, como muestran los ejemplos, y así conservamos los datos de partida.

4️⃣ Retiramos permisos con REVOKE​

Si una cuenta deja de necesitar un permiso, debemos retirarlo. REVOKE permite quitar privilegios previamente concedidos sin eliminar la cuenta.

La sintaxis general es:

REVOKE privilegio [, privilegio ...]
ON base_datos.objeto
FROM 'usuario'@'host';

🔶 Retiramos el permiso de modificación​

Supongamos que gestion_tic ya no necesita actualizar incidencias; a partir de ahora solo podrá consultarlas.

Paso 1. Retiramos el privilegio

Desde la consola administrativa de MySQL en la VM:

REVOKE UPDATE ON soporte_tic.incidencias
FROM 'gestion_tic'@'localhost';

Paso 2. Consultamos los privilegios restantes

SHOW GRANTS FOR 'gestion_tic'@'localhost';

Resultado esperado:

GRANT USAGE ON *.* TO `gestion_tic`@`localhost`
GRANT SELECT ON `soporte_tic`.`incidencias` TO `gestion_tic`@`localhost`
en este ejemplo

La cuenta conserva SELECT, pero ya no aparece UPDATE. REVOKE ha retirado únicamente el permiso solicitado, sin eliminar la cuenta ni su permiso de consulta.

🔶 Comprobamos que se ha retirado el permiso​

Desde una nueva ventana de CMD de la VM, iniciamos sesión como gestion_tic:

mysql --default-character-set=utf8mb4 -u gestion_tic -p

Intentamos modificar una incidencia:

UPDATE soporte_tic.incidencias
SET estado = 'en_proceso'
WHERE id_incidencia = 1;

Resultado esperado: MySQL rechaza el UPDATE por falta de privilegios. La cuenta sigue pudiendo consultar:

SELECT id_incidencia, titulo, estado
FROM soporte_tic.incidencias
WHERE id_incidencia = 1;

Si la consulta devuelve la incidencia, hemos comprobado que REVOKE retiró un permiso sin eliminar la cuenta ni el resto de sus privilegios.

REVOKE no elimina la cuenta
  • REVOKE retira privilegios, pero la cuenta sigue existiendo.
  • DROP USER elimina la cuenta del servidor.
Estado del laboratorio

Al finalizar este apartado, las cuentas consulta_tic, registro_tic y gestion_tic siguen existiendo. Las dos primeras conservan los privilegios concedidos inicialmente, mientras que gestion_tic ha quedado únicamente con permiso SELECT después de retirar UPDATE.

Las comprobaciones realizadas dentro de transacciones se han deshecho mediante ROLLBACK, por lo que conservamos los datos iniciales de soporte_tic.

🔎 Para saber más: otras opciones de gestión de privilegios​

🔶 Privilegios sobre columnas​

MySQL permite limitar determinados permisos a columnas concretas. Por ejemplo, autorizar cambios en estado, pero no en otras columnas de la tabla:

GRANT UPDATE (estado) ON soporte_tic.incidencias
TO 'gestion_tic'@'localhost';

Esta instrucción es un ejemplo de ampliación, no debe ejecutarse como parte de la práctica principal, porque modificaría los permisos que acabamos de comprobar.

📖 Documentación oficial: GRANT

🔶 Delegación de privilegios​

La opción WITH GRANT OPTION permite que una cuenta conceda a otras cuentas determinados privilegios que posee. Debe utilizarse con precaución, porque supone delegar la capacidad de conceder permisos.

GRANT SELECT ON soporte_tic.incidencias
TO 'consulta_tic'@'localhost'
WITH GRANT OPTION;

No ejecutes este ejemplo en el laboratorio básico: las cuentas de prueba no necesitan delegar permisos.

📖 Documentación oficial: GRANT y WITH GRANT OPTION

🔶 Conceder todos los privilegios con ALL PRIVILEGES​

MySQL permite conceder todos los privilegios disponibles para un ámbito determinado mediante ALL PRIVILEGES.

Por ejemplo:

GRANT ALL PRIVILEGES ON soporte_tic.*
TO 'usuario'@'localhost';

Esta instrucción concede todos los privilegios aplicables a la base de datos soporte_tic, pero no incluye automáticamente GRANT OPTION, que permite delegar privilegios.

warning

No ejecutes este ejemplo en el laboratorio. Conceder todos los privilegios suele ser innecesario para las cuentas de una aplicación y contradice el principio de mínimo privilegio.

📖 Documentación oficial: GRANT

🔶 Consultar privilegios mediante INFORMATION_SCHEMA​

Además de SHOW GRANTS, MySQL permite consultar información sobre los privilegios concedidos mediante las vistas de INFORMATION_SCHEMA.

VistaInformación que proporciona
USER_PRIVILEGESPrivilegios globales concedidos a cuentas.
SCHEMA_PRIVILEGESPrivilegios concedidos sobre bases de datos.
TABLE_PRIVILEGESPrivilegios concedidos sobre tablas.

Por ejemplo, desde una sesión administrativa podemos consultar los privilegios concedidos directamente sobre las tablas de soporte_tic:

SELECT GRANTEE, TABLE_NAME, PRIVILEGE_TYPE
FROM information_schema.TABLE_PRIVILEGES
WHERE TABLE_SCHEMA = 'soporte_tic';

Cada fila identifica una cuenta, una tabla y un privilegio.

Estas consultas complementan a SHOW GRANTS, pero no lo sustituyen: cada vista recoge privilegios concedidos en un ámbito concreto y no representa necesariamente todos los permisos efectivos de una cuenta.

📖 Documentación oficial: TABLE_PRIVILEGES

5️⃣ ¿Qué hemos conseguido?​

Hemos aprendido a conceder, consultar, comprobar y retirar privilegios:

NecesidadInstrucción
Conceder permisos.GRANT
Consultar los permisos de una cuenta.SHOW GRANTS
Retirar permisos.REVOKE

Al terminar, consulta_tic podrá consultar incidencias; registro_tic podrá consultarlas y registrarlas; y gestion_tic habrá quedado únicamente con permisos de consulta después de retirar UPDATE.

para pensar

En una empresa trabajan cinco técnicos que necesitan los mismos privilegios. Si los concedemos uno a uno, ¿qué ocurrirá cuando haya que cambiar los permisos de todos?
