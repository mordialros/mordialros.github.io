4.1. Gestión de usuarios en MySQL

En la UT3 dejamos MySQL funcionando y permitimos conexiones desde el anfitrión. Ahora debemos resolver otra necesidad: identificar quién se conecta al servidor y decidir desde qué equipo puede hacerlo.

Imaginemos una empresa que gestiona incidencias informáticas. Se incorpora una persona al equipo de soporte y necesita consultar la base de datos. Antes de pensar en qué datos podrá ver, el administrador debe preparar una cuenta de MySQL para que pueda autenticarse.

En este apartado aprenderemos a crear, comprobar, modificar y eliminar cuentas. Los permisos sobre las tablas se trabajarán en el siguiente apartado.

Dónde trabajamos
  • VM con Windows 11 Pro: utilizamos la consola de MySQL para administrar el servidor mediante SQL. En el apartado 4.6 utilizaremos también MySQL Workbench, instalado en la VM, para administrar cuentas y privilegios desde su interfaz gráfica.
  • Anfitrión: mantenemos Workbench para comprobar conexiones remotas con cuentas limitadas, como en la UT3.
  • Base de datos de referencia: soporte_tic, ya creada. Aquí no modificamos sus tablas.

Las instrucciones SQL se escriben en el indicador mysql>. Los comandos que empiezan por mysql -u se ejecutan en el Símbolo del sistema de Windows, fuera de la consola de MySQL.

1️⃣ Diferenciamos los usuarios de una aplicación y las cuentas de MySQL​

En la base de datos soporte_tic existe una tabla usuarios con las personas que comunican incidencias. Esos registros no son cuentas de acceso al servidor MySQL.

Usuarios de la aplicaciónCuentas de MySQL
Son datos que guarda la aplicación en una tabla.Son identidades que MySQL utiliza para autenticar conexiones.
Por ejemplo, una persona que comunica que su impresora no funciona.Por ejemplo, una cuenta utilizada por el servicio de gestión de incidencias.
Los gestiona la lógica de la aplicación.Las administra una cuenta con los privilegios correspondientes en MySQL.

En muchas aplicaciones reales, los empleados entran en la aplicación con sus propias credenciales y es la aplicación la que se conecta a MySQL mediante una cuenta de servicio. No es necesario crear una cuenta MySQL por cada persona que utiliza la aplicación.

En nuestro laboratorio crearemos cuentas MySQL individuales para aprender a administrar y comprobar el acceso al servidor.

2️⃣ Entendemos cómo identifica MySQL una cuenta​

MySQL identifica una cuenta mediante la combinación de nombre de usuario y origen autorizado:

'usuario'@'host'
EjemploQué significa
'root'@'localhost'Cuenta root utilizada desde el propio servidor.
'soporte_prueba'@'localhost'Cuenta de prueba para conectarse desde la VM.
'soporte_prueba'@'192.168.10.1'Cuenta de prueba para un cliente cuyo origen sea esa IP.

La dirección 192.168.10.1 es ficticia: en nuestro laboratorio debe sustituirse por la IPv4 real de VMnet8 del anfitrión, que identificamos en la UT3.

Importante

El host de la cuenta identifica desde dónde llega el cliente, no la dirección del servidor. No utilizamos '%' por comodidad: permitiría que la cuenta coincidiera con un conjunto mucho más amplio de orígenes.

Dos cuentas con el mismo nombre de usuario y diferente host pueden tener contraseñas y privilegios distintos.

3️⃣ Creamos una cuenta de MySQL​

Vamos a preparar una cuenta para una persona del servicio de soporte que, de momento, solo necesita poder conectarse desde la propia VM.

En la consola MySQL de la VM, con la sesión administrativa, ejecutamos:

CREATE USER 'soporte_prueba'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_CLAVE_PROPIA';
en este ejemplo
  • CREATE USER crea una cuenta en el servidor.
  • 'soporte_prueba'@'localhost' identifica la cuenta y su origen.
  • IDENTIFIED BY establece la contraseña.

El texto de la contraseña es un marcador, no una clave que debamos reutilizar. Cada alumno lo sustituye por una contraseña propia para el laboratorio; no se publica en capturas ni entregas.

Autenticación y autorización

Crear una cuenta con CREATE USER permite que una persona o aplicación se identifique ante MySQL mediante sus credenciales (autenticación). Pero esto no significa que pueda consultar o modificar las bases de datos.

Para realizar esas operaciones, la cuenta necesita los privilegios correspondientes (autorización).

Por ejemplo, soporte_prueba puede conectarse correctamente al servidor, pero no consultar soporte_tic.incidencias hasta que le concedamos el privilegio SELECT.

🔶 Comprobamos que la cuenta existe​

Desde la misma sesión administrativa:

SELECT User, Host
FROM mysql.user
WHERE User = 'soporte_prueba';

La consulta debe mostrar la cuenta y el origen localhost.

También podemos comprobar qué permisos tiene inicialmente:

SHOW GRANTS FOR 'soporte_prueba'@'localhost';

Es normal que aparezca USAGE sobre *.*. Esto indica que la cuenta existe, pero todavía no tiene permisos para consultar o modificar los datos de las bases de datos.

🔶 Probamos la conexión con la nueva cuenta​

En la VM, abrimos una nueva ventana del Símbolo del sistema, no una nueva instrucción dentro de mysql>:

mysql --default-character-set=utf8mb4 -u soporte_prueba -p -h localhost

Introduce la contraseña de soporte_prueba cuando se solicite.

Si las credenciales son correctas, MySQL permitirá iniciar sesión con esta cuenta. A diferencia de root, soporte_prueba no tiene permisos administrativos ni acceso a las tablas de soporte_tic.

Para comprobar con qué cuenta hemos iniciado sesión, ejecutamos:

SELECT USER(), CURRENT_USER();

USER() muestra la identidad y el origen con los que se presentó el cliente; CURRENT_USER() identifica la cuenta que MySQL utilizó para autenticarlo.

Prueba a ejecutar:

SELECT * FROM soporte_tic.incidencias;

Resultado esperado: MySQL rechaza la consulta por falta de permisos sobre la tabla. Esto no significa que haya fallado la conexión: la cuenta ha conseguido autenticarse, pero todavía no está autorizada para consultar esos datos.

Para cerrar la sesión limitada:

EXIT;
¿Y si queremos conectarnos desde Workbench?

Como vimos en la UT3, para conectarnos desde el anfitrión necesitamos una cuenta cuyo host coincida con el origen de la conexión, además de tener configurada la conectividad con el servidor.

La cuenta 'soporte_prueba'@'localhost' solo está preparada para conexiones locales desde la VM, por lo que no podemos utilizarla para conectarnos desde el anfitrión.

4️⃣ Modificamos una cuenta existente​

Si una persona necesita cambiar su contraseña, no debemos eliminar su cuenta y crearla de nuevo. Podemos modificarla.

En la consola administrativa de MySQL:

ALTER USER 'soporte_prueba'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_OTRA_CLAVE_PROPIA';
en este ejemplo

ALTER USER modifica una cuenta existente. En este caso cambia su contraseña, pero no concede ni retira privilegios sobre las tablas.

La contraseña escrita en una instrucción SQL puede quedar expuesta en el historial o en registros, según el entorno. Utilizamos contraseñas de laboratorio que no se reutilicen y evitamos mostrarlas o entregarlas. En producción se seguirían los procedimientos seguros establecidos por la organización.

Comprobamos el cambio cerrando la conexión limitada anterior y abriendo otra con la contraseña nueva. La antigua ya no debería permitir iniciar una sesión nueva.

5️⃣ Eliminamos una cuenta que ya no se necesita​

Cuando una cuenta de prueba deja de ser necesaria, el administrador puede eliminarla:

DROP USER 'soporte_prueba'@'localhost';

Para comprobarlo, repetimos la consulta:

SELECT User, Host
FROM mysql.user
WHERE User = 'soporte_prueba';

El resultado debe estar vacío si no existen otras cuentas con ese nombre.

Antes de eliminar una cuenta

No utilizamos DROP USER sobre root, las cuentas internas de MySQL ni cuentas que no hayamos creado para la práctica.

En un entorno profesional, antes de eliminar una cuenta debemos comprobar que ya no se utiliza, para evitar interrumpir el acceso de personas o aplicaciones que todavía la necesitan.

Estado del laboratorio

Al finalizar este apartado, la cuenta de prueba soporte_prueba ha sido eliminada. La base de datos soporte_tic permanece sin cambios.

🔎 Para saber más: otras opciones de administración de cuentas​

MySQL dispone de otras funcionalidades para administrar las cuentas y reforzar su seguridad. Aunque no las utilizaremos en las prácticas de esta unidad, conviene conocerlas.

🔶 Bloqueo y desbloqueo de cuentas​

Permite impedir temporalmente que una cuenta establezca nuevas conexiones, sin necesidad de eliminarla ni perder los privilegios que tiene asignados.

Por ejemplo, puede utilizarse cuando una persona deja de necesitar acceso durante un periodo de tiempo.

-- Bloquear una cuenta
ALTER USER 'soporte_prueba'@'localhost' ACCOUNT LOCK;

-- Desbloquearla
ALTER USER 'soporte_prueba'@'localhost' ACCOUNT UNLOCK;

📖 Documentación oficial: bloqueo de cuentas

🔶 Caducidad de contraseñas​

Permite exigir que una cuenta cambie su contraseña, por ejemplo, cuando se considera que puede haber quedado comprometida.

-- Marcar la contraseña como caducada
ALTER USER 'soporte_prueba'@'localhost' PASSWORD EXPIRE;

Cuando la cuenta vuelva a conectarse, deberá cambiar su contraseña antes de realizar operaciones normales, utilizando un cliente que admita este proceso.

También es posible configurar un periodo de caducidad mediante PASSWORD EXPIRE INTERVAL.

📖 Documentación oficial: caducidad de contraseñas

🔶 Consulta de la definición de una cuenta​

La instrucción SHOW CREATE USER permite consultar cómo está configurada una cuenta de MySQL, incluyendo sus opciones de autenticación y seguridad.

SHOW CREATE USER 'soporte_prueba'@'localhost';

Esta información puede resultar útil para revisar la configuración de una cuenta antes de modificarla.

📖 Documentación oficial: SHOW CREATE USER
