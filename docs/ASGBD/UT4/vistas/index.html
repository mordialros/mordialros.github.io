4.4. Vistas y control de acceso en MySQL

En los apartados anteriores hemos creado cuentas, concedido privilegios y agrupado permisos mediante roles. Ahora debemos resolver una situación habitual de administración: una cuenta necesita consultar determinados datos, pero no debe acceder directamente a toda la tabla.

En nuestro gestor de incidencias, el personal de consulta necesita ver los datos básicos de todas las incidencias, mientras que el personal de seguimiento necesita centrarse en las que todavía están pendientes de resolución. Como administradores, prepararemos una vista para cada necesidad y comprobaremos cómo limitar su acceso mediante privilegios.

Dónde trabajamos
  • VM con Windows 11 Pro: utilizamos la consola de MySQL para administrar el servidor mediante SQL. En el apartado 4.6 utilizaremos también MySQL Workbench, instalado en la VM, para administrar cuentas y privilegios desde su interfaz gráfica.
  • Anfitrión: mantenemos Workbench para comprobar conexiones remotas con cuentas limitadas, como en la UT3.
  • Base de datos: soporte_tic, cargada al comenzar la unidad.

Los comandos mysql -u ... se ejecutan desde CMD. Las instrucciones SQL se ejecutan cuando aparece mysql>.

1️⃣ ¿Por qué utiliza vistas un administrador?​

Una vista es un objeto definido mediante una consulta SELECT. Este concepto puede resultar familiar de GBD; aquí lo utilizaremos para administrar el acceso a la información, no para practicar consultas complejas.

Una vista permite presentar solo las columnas o filas que necesita un determinado perfil y asignar permisos sobre ella, sin tener que conceder acceso directo a todas las tablas originales.

Tabla incidenciasVista vista_incidencias
Incluye todos los campos de cada incidencia.Inicialmente muestra id_incidencia, titulo y estado.
Almacena los registros.Presenta el resultado de una consulta; no crea una copia independiente de los registros.
Requiere permisos sobre la tabla para consultarla directamente.Podemos conceder permisos específicos sobre la vista.
Una vista no sustituye a los privilegios

La vista define qué información se presenta; los privilegios determinan qué cuentas pueden utilizarla. Para proteger los datos, debemos configurar y comprobar ambas cosas.

2️⃣ Preparamos vistas para distintos perfiles​

En la empresa de soporte informático distinguimos dos necesidades:

  • Personal de consulta: necesita consultar los datos básicos de todas las incidencias.
  • Personal de seguimiento: necesita consultar únicamente las incidencias abiertas o en proceso.

Crearemos una vista para cada perfil. Más adelante comprobaremos qué permisos necesita cada cuenta para acceder a ellas.

La sintaxis básica es:

CREATE VIEW base_datos.nombre_vista AS
SELECT columnas
FROM base_datos.tabla
[WHERE condicion];
  • nombre_vista: nombre del objeto que creamos.
  • SELECT: consulta que define la información presentada.
  • WHERE: condición opcional para seleccionar determinadas filas.

🔶 Vista con los datos básicos de las incidencias​

La empresa necesita mostrar un catálogo sencillo de incidencias. Prepararemos una vista con su identificador, título y estado.

Paso 1. Creamos la vista

Desde la consola administrativa de MySQL de la VM:

CREATE VIEW soporte_tic.vista_incidencias AS
SELECT id_incidencia, titulo, estado
FROM soporte_tic.incidencias;

MySQL confirma su creación con Query OK, 0 rows affected.

Paso 2. Comprobamos que existe

SHOW FULL TABLES FROM soporte_tic
WHERE Table_type = 'VIEW';

En nuestra comprobación apareció:

+-----------------------+------------+
| Tables_in_soporte_tic | Table_type |
+-----------------------+------------+
| vista_incidencias     | VIEW       |
+-----------------------+------------+

Paso 3. Consultamos la vista

SELECT * FROM soporte_tic.vista_incidencias;

Entre los registros obtenidos se encontraban:

+---------------+-----------------------------+------------+
| id_incidencia | titulo                      | estado     |
+---------------+-----------------------------+------------+
|             1 | No se puede iniciar sesión  | abierta    |
|             2 | Impresora sin conexión      | en_proceso |
|             3 | Red lenta                   | en_proceso |
+---------------+-----------------------------+------------+
en este ejemplo

MySQL identifica vista_incidencias como una vista, no como una tabla. Podemos consultarla con SELECT de manera parecida a una tabla, pero solo devuelve las columnas que aparecen en su definición. En la comprobación completa se obtuvieron 12 incidencias.

🔶 Vista para el seguimiento de incidencias​

El personal de seguimiento necesita centrarse en las incidencias que todavía requieren atención. Para ello, creamos una segunda vista que utiliza WHERE para mostrar únicamente las incidencias abiertas o en proceso.

Desde la consola administrativa de MySQL de la VM:

CREATE VIEW soporte_tic.vista_pendientes AS
SELECT id_incidencia, titulo, estado
FROM soporte_tic.incidencias
WHERE estado IN ('abierta', 'en_proceso');

Comprobamos los registros obtenidos:

SELECT * FROM soporte_tic.vista_pendientes;

Para comprobar cuántas incidencias cumplen la condición, ejecutamos:

SELECT COUNT(*) AS total_pendientes
FROM soporte_tic.vista_pendientes;
en este ejemplo

vista_incidencias muestra las 12 incidencias, mientras que vista_pendientes muestra solo aquellas cuyo estado es abierta o en_proceso. La consulta COUNT(*) permite comprobar cuántas cumplen la condición, sin modificar la tabla original.

3️⃣ Adaptamos la vista a los requisitos del perfil​

Ahora la empresa solicita que el catálogo muestre también la prioridad de cada incidencia.

La sintaxis básica es:

ALTER VIEW base_datos.nombre_vista AS
SELECT columnas
FROM base_datos.tabla
[WHERE condicion];

🔶 Añadimos la prioridad al catálogo​

Paso 1. Modificamos la definición

Desde la consola administrativa de MySQL de la VM:

ALTER VIEW soporte_tic.vista_incidencias AS
SELECT id_incidencia, titulo, estado, prioridad
FROM soporte_tic.incidencias;

Paso 2. Comprobamos el resultado

SELECT * FROM soporte_tic.vista_incidencias;

Parte del resultado obtenido:

+---------------+-----------------------------+------------+-----------+
| id_incidencia | titulo                      | estado     | prioridad |
+---------------+-----------------------------+------------+-----------+
|             1 | No se puede iniciar sesión  | abierta    | alta      |
|             2 | Impresora sin conexión      | en_proceso | media     |
|             3 | Red lenta                   | en_proceso | alta      |
+---------------+-----------------------------+------------+-----------+
en este ejemplo

La vista ahora muestra cuatro columnas. No hemos añadido una columna a la tabla incidencias: solo hemos cambiado qué información incluye la consulta que define la vista.

4️⃣ Concedemos acceso a la vista y comprobamos la seguridad​

La empresa necesita una cuenta que consulte el catálogo, pero no pueda acceder directamente a todos los campos de la tabla incidencias.

🔶 Concedemos acceso a la vista​

Paso 1. Preparamos una cuenta limitada

Desde la consola administrativa de MySQL en la VM:

CREATE USER 'consulta_vistas'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_CLAVE_PROPIA';

La contraseña es un marcador: utiliza una clave de prueba propia. Si ya has creado esta cuenta durante las comprobaciones, no vuelvas a ejecutar CREATE USER.

Paso 2. Concedemos permiso de consulta únicamente sobre la vista

GRANT SELECT ON soporte_tic.vista_incidencias
TO 'consulta_vistas'@'localhost';

Paso 3. Consultamos los privilegios

SHOW GRANTS FOR 'consulta_vistas'@'localhost';

Si la cuenta no tiene otros privilegios, esperamos una concesión equivalente a esta:

GRANT USAGE ON *.* TO `consulta_vistas`@`localhost`
GRANT SELECT ON `soporte_tic`.`vista_incidencias` TO `consulta_vistas`@`localhost`
en este ejemplo

SELECT se ha concedido sobre vista_incidencias, no sobre la tabla incidencias. USAGE ON *.* no añade permisos de lectura sobre todas las bases de datos, como vimos en el 4.2.

Esta salida se muestra como resultado esperado; la comprobación decisiva será realizar las consultas con la cuenta limitada.

🔶 Comprobamos las operaciones permitidas y denegadas​

Paso 1. Nos conectamos con la cuenta limitada

Abrimos otra ventana de CMD en la VM:

mysql --default-character-set=utf8mb4 -u consulta_vistas -p

Paso 2. Comprobamos el acceso permitido

Dentro de MySQL:

SELECT * FROM soporte_tic.vista_incidencias;

En nuestra prueba la consulta mostró las 12 incidencias con las cuatro columnas autorizadas.

Paso 3. Comprobamos el acceso denegado

SELECT * FROM soporte_tic.incidencias;

MySQL devolvió el siguiente error real:

ERROR 1142 (42000): SELECT command denied to user 'consulta_vistas'@'localhost' for table 'incidencias'
en este ejemplo

La cuenta puede consultar la vista, pero MySQL rechaza el acceso directo a la tabla original. Así podemos ofrecer la información necesaria sin conceder acceso a todas las columnas de incidencias.

Esto es posible porque nuestra vista se creó con el contexto de seguridad predeterminado, SQL SECURITY DEFINER: para acceder a la tabla original a través de la vista se comprueban los privilegios de la cuenta que la definió, mientras que consulta_vistas necesita el permiso correspondiente sobre la propia vista. No significa que la cuenta limitada pueda consultar la tabla directamente.

para pensar

Hemos preparado dos vistas: vista_incidencias y vista_pendientes.

Crea una cuenta MySQL para el personal de seguimiento y configura sus privilegios para que:

  • Pueda consultar vista_pendientes.
  • No pueda consultar vista_incidencias.
  • No pueda acceder directamente a la tabla incidencias.

Conéctate con esa cuenta y comprueba las tres situaciones. ¿Qué consultas funcionan y cuáles son rechazadas?

Precaución de seguridad

Las vistas deben diseñarse cuidadosamente: no basta con ocultar algunas columnas si también se han concedido permisos directos sobre la tabla original. Además, conviene evitar que una cuenta utilizada para definir vistas tenga más privilegios de los necesarios en un entorno de producción.

5️⃣ Eliminamos una vista con DROP VIEW​

Cuando una vista deja de ser necesaria, podemos eliminarla sin borrar la tabla de la que obtiene sus datos.

Su sintaxis básica es:

DROP VIEW base_datos.nombre_vista;

🔶 Eliminamos la vista de incidencias​

Paso 1. Eliminamos la vista

Desde la consola administrativa de MySQL de la VM:

DROP VIEW soporte_tic.vista_incidencias;

Paso 2. Comprobamos que ya no existe

SHOW FULL TABLES FROM soporte_tic
WHERE Table_type = 'VIEW';

Resultado esperado, si solo hemos creado las dos vistas de este apartado:

+-----------------------+------------+
| Tables_in_soporte_tic | Table_type |
+-----------------------+------------+
| vista_pendientes      | VIEW       |
+-----------------------+------------+

Paso 3. Comprobamos que la tabla original permanece

SELECT COUNT(*) AS total_incidencias
FROM soporte_tic.incidencias;

Si conservamos los datos iniciales, el resultado debe ser 12 incidencias.

en este ejemplo

DROP VIEW elimina la definición de la vista, pero no elimina la tabla incidencias ni sus registros. vista_pendientes sigue disponible, porque no la hemos eliminado.

Estado del laboratorio

Al finalizar este apartado, vista_incidencias ha sido eliminada, mientras que vista_pendientes continúa existiendo.

La cuenta consulta_vistas sigue creada, aunque la vista que utilizaba ya no existe. Si has realizado la comprobación autónoma, también permanecerá la cuenta que hayas creado para el personal de seguimiento.

Los datos originales de soporte_tic no se han modificado.

🔎 Para saber más: otras posibilidades de las vistas​

🔶 Vistas actualizables​

Algunas vistas permiten modificar los datos de las tablas originales mediante INSERT, UPDATE o DELETE, siempre que su definición lo permita y la cuenta disponga de los privilegios necesarios.

Por ejemplo, una vista sencilla basada en una única tabla puede admitir modificaciones, mientras que una vista que utiliza agrupaciones no suele ser actualizable.

Una vista no es una copia independiente de los datos: las modificaciones realizadas a través de una vista actualizable afectan a la tabla original.

📖 Documentación oficial: vistas actualizables

🔶 Opciones de seguridad DEFINER e INVOKER​

MySQL permite configurar qué cuenta se utiliza para comprobar los privilegios necesarios sobre las tablas a las que accede una vista:

  • SQL SECURITY DEFINER: se utilizan los privilegios de la cuenta definida como creadora o definidora de la vista. Es el comportamiento predeterminado.
  • SQL SECURITY INVOKER: se utilizan los privilegios de la cuenta que ejecuta la consulta sobre la vista.

Una forma de indicar explícitamente la primera opción es:

CREATE SQL SECURITY DEFINER VIEW soporte_tic.vista_ejemplo AS
SELECT id_incidencia, titulo
FROM soporte_tic.incidencias;

Es un ejemplo de ampliación: no necesitamos ejecutarlo para completar las comprobaciones anteriores.

📖 Documentación oficial: seguridad de las vistas

6️⃣ ¿Qué hemos conseguido como administradores?​

Hemos aprendido a preparar vistas para distintos perfiles, conceder acceso a una de ellas y comprobar los límites de ese acceso. También sabemos modificar y eliminar una vista y reconocer que algunas admiten actualizaciones.

NecesidadInstrucción
Crear una vista.CREATE VIEW
Modificar su definición.ALTER VIEW
Conceder acceso a la vista.GRANT SELECT
Comprobar permisos.SHOW GRANTS y consultas con la cuenta limitada
Eliminar una vista.DROP VIEW
para pensar

En el gestor de incidencias, una cuenta debe consultar el título y el estado de las incidencias, pero no los datos de las personas que las comunicaron. ¿Por qué crear una vista y conceder acceso solo a ella puede ser más adecuado que dar permiso SELECT sobre toda la tabla incidencias?
