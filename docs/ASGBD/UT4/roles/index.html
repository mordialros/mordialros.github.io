4.3. Gestión de roles en MySQL

En el 4.2 concedimos privilegios directamente a cuentas como consulta_tic y gestion_tic. Ese sistema funciona, pero ¿qué ocurriría si cinco técnicos necesitan los mismos permisos y la empresa decide cambiarlos?

Podríamos ejecutar GRANT o REVOKE para cada cuenta, una por una. Sin embargo, como administradores nos interesa gestionar conjuntamente los permisos que corresponden a un mismo trabajo.

Para eso utilizaremos los roles.

Dónde trabajamos
  • Servidor (VM con Windows 11 Pro): consola de MySQL con la cuenta administrativa local para crear roles, concederles privilegios y asignarlos.
  • Comprobaciones: nuevas sesiones locales de MySQL con las cuentas limitadas tecnico1 y tecnico2.
  • Base de datos: soporte_tic, creada al comienzo de la unidad.

Los comandos mysql -u ... se ejecutan en CMD de la VM. Las sentencias SQL se ejecutan cuando aparece mysql>.

1️⃣ ¿Qué es un rol y para qué sirve?​

Un rol es un conjunto de privilegios al que asignamos un nombre. En lugar de conceder los mismos permisos a cada cuenta, concedemos los permisos al rol y asignamos ese rol a las cuentas que los necesitan.

Por ejemplo, los técnicos de una empresa deben consultar las incidencias y actualizar su estado. Creamos rol_tecnico con los privilegios SELECT y UPDATE sobre soporte_tic.incidencias y lo asignamos a las cuentas de los técnicos.

Sin rolesCon roles
Concedemos SELECT y UPDATE a cada técnico.Concedemos SELECT y UPDATE a rol_tecnico.
Si cambian los permisos, modificamos varias cuentas.Si cambian los permisos, modificamos el rol.
Es más fácil olvidar alguna cuenta.Los cambios se aplican a quienes utilizan ese rol.
Una diferencia importante

Una cuenta identifica a quien se conecta; un rol agrupa privilegios. Los roles no sustituyen a las cuentas de los técnicos: se les asignan para que puedan utilizar los permisos agrupados.

2️⃣ Creamos un rol y agrupamos privilegios​

Utilizaremos un rol que permita consultar y modificar incidencias, pero no insertarlas ni eliminarlas.

La sintaxis básica para crear un rol es:

CREATE ROLE 'nombre_rol'@'host';

Como ocurre con las cuentas, MySQL identifica el rol por su nombre y la parte @'host'. En nuestros ejemplos empleamos 'rol_tecnico'@'%', que será el identificador del rol. Esto no significa que estemos habilitando conexiones remotas para una cuenta de administrador.

🔶 Preparamos el rol de los técnicos​

Las instrucciones siguientes se ejecutan desde la consola administrativa de MySQL en la VM.

Paso 1. Creamos el rol

CREATE ROLE 'rol_tecnico'@'%';

Paso 2. Concedemos privilegios al rol

GRANT SELECT, UPDATE ON soporte_tic.incidencias
TO 'rol_tecnico'@'%';

El mismo GRANT que aprendimos en el 4.2 sirve para conceder permisos a un rol, en lugar de a una cuenta individual.

Paso 3. Consultamos los privilegios del rol

SHOW GRANTS FOR 'rol_tecnico'@'%';

MySQL muestra:

GRANT USAGE ON *.* TO `rol_tecnico`@`%`
GRANT SELECT, UPDATE ON `soporte_tic`.`incidencias` TO `rol_tecnico`@`%`
en este ejemplo

La segunda línea confirma que rol_tecnico agrupa SELECT y UPDATE sobre incidencias. El rol no tiene permisos para insertar ni eliminar incidencias.

La línea USAGE ON *.* no concede privilegios globales, como vimos en el 4.2.

3️⃣ Asignamos el rol a las cuentas​

Ahora tenemos dos técnicos que necesitan utilizar esos permisos. Primero crearemos sus cuentas y después les asignaremos el mismo rol.

La sintaxis para asignar un rol es:

GRANT 'nombre_rol'@'host'
TO 'usuario'@'host';

Fíjate en la diferencia: para conceder privilegios utilizamos GRANT ... ON ... TO ...; para asignar un rol utilizamos GRANT rol TO usuario, sin ON.

🔶 Asignamos rol_tecnico a dos técnicos​

Paso 1. Creamos las cuentas

Desde la sesión administrativa de MySQL en la VM:

CREATE USER 'tecnico1'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_CLAVE_PROPIA';

CREATE USER 'tecnico2'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_CLAVE_PROPIA';

Sustituye los marcadores por contraseñas propias de laboratorio. Si las cuentas ya existen, no vuelvas a crearlas: continúa con la asignación del rol.

Paso 2. Asignamos el rol a las dos cuentas

GRANT 'rol_tecnico'@'%'
TO 'tecnico1'@'localhost',
   'tecnico2'@'localhost';

Paso 3. Consultamos los roles asignados

SHOW GRANTS FOR 'tecnico1'@'localhost';
SHOW GRANTS FOR 'tecnico2'@'localhost';

Para tecnico1, MySQL muestra:

GRANT USAGE ON *.* TO `tecnico1`@`localhost`
GRANT `rol_tecnico`@`%` TO `tecnico1`@`localhost`

En tecnico2 obtenemos las mismas líneas, con su nombre de cuenta.

en este ejemplo

La segunda línea confirma que el rol está asignado a la cuenta. No aparece directamente SELECT ni UPDATE porque esos permisos pertenecen al rol, no se concedieron individualmente a cada técnico.

Tener un rol asignado no significa necesariamente tenerlo activo en una sesión. Lo comprobaremos a continuación.

4️⃣ Activamos el rol y comprobamos los permisos​

Para que una cuenta pueda utilizar los privilegios de un rol, el rol debe estar activo. Un rol concedido puede permanecer inactivo al iniciar sesión.

Podemos configurar un rol predeterminado, que se activará al establecer nuevas conexiones:

SET DEFAULT ROLE 'nombre_rol'@'host'
TO 'usuario'@'host';

🔶 Activamos el rol por defecto​

Paso 1. Configuramos el rol predeterminado

Desde la consola administrativa de MySQL en la VM:

SET DEFAULT ROLE 'rol_tecnico'@'%'
TO 'tecnico1'@'localhost',
   'tecnico2'@'localhost';

Paso 2. Nos conectamos como tecnico1

En una nueva ventana de CMD de la VM:

mysql --default-character-set=utf8mb4 -u tecnico1 -p

Dentro de la sesión limitada, comprobamos el rol activo:

SELECT CURRENT_ROLE();

El resultado que obtuvimos fue:

+---------------------+
| CURRENT_ROLE()      |
+---------------------+
| `rol_tecnico`@`%`   |
+---------------------+
en este ejemplo

CURRENT_ROLE() identifica los roles activos en la sesión actual. El resultado confirma que tecnico1 puede utilizar los privilegios de rol_tecnico.

No es suficiente con comprobar que el rol está asignado mediante SHOW GRANTS: también debemos comprobar que está activo cuando el usuario se conecta.

Paso 3. Comprobamos las operaciones permitidas

Desde la misma sesión de tecnico1, consultamos una incidencia:

SELECT id_incidencia, titulo, estado
FROM soporte_tic.incidencias
WHERE id_incidencia = 1;

En nuestro laboratorio se obtuvo:

+---------------+-----------------------------+---------+
| id_incidencia | titulo                      | estado  |
+---------------+-----------------------------+---------+
|             1 | No se puede iniciar sesión  | abierta |
+---------------+-----------------------------+---------+

También comprobamos que puede modificar su estado, sin conservar el cambio:

START TRANSACTION;

UPDATE soporte_tic.incidencias
SET estado = 'en_proceso'
WHERE id_incidencia = 1;

ROLLBACK;

MySQL confirmó la actualización con Query OK, 1 row affected. Después, ROLLBACK deshizo el cambio.

en este ejemplo

Las operaciones SELECT y UPDATE funcionan porque la sesión tiene activo rol_tecnico. No hemos concedido estos permisos directamente a tecnico1: los recibe a través del rol.

5️⃣ Modificamos los privilegios de un rol​

La empresa decide que, a partir de ahora, los técnicos solo podrán consultar incidencias. En lugar de retirar UPDATE a cada usuario, lo retiramos una vez del rol.

🔶 Retiramos UPDATE del rol​

Paso 1. Retiramos el privilegio

Desde la consola administrativa de MySQL en la VM:

REVOKE UPDATE ON soporte_tic.incidencias
FROM 'rol_tecnico'@'%';

Paso 2. Consultamos los privilegios restantes

SHOW GRANTS FOR 'rol_tecnico'@'%';

El resultado obtenido fue:

GRANT USAGE ON *.* TO `rol_tecnico`@`%`
GRANT SELECT ON `soporte_tic`.`incidencias` TO `rol_tecnico`@`%`
en este ejemplo

El rol conserva SELECT, pero ya no tiene UPDATE. No hemos tenido que ejecutar un REVOKE para tecnico1 y otro para tecnico2.

Paso 3. Comprobamos que la modificación se rechaza

Abrimos una nueva conexión como tecnico1 desde CMD de la VM:

mysql --default-character-set=utf8mb4 -u tecnico1 -p

En MySQL intentamos modificar una incidencia:

UPDATE soporte_tic.incidencias
SET estado = 'resuelta'
WHERE id_incidencia = 1;

MySQL devolvió:

ERROR 1142 (42000): UPDATE command denied to user 'tecnico1'@'localhost' for table 'incidencias'
en este ejemplo

El servidor rechaza el UPDATE porque hemos retirado ese permiso del rol. El cambio afecta a las cuentas que dependen de ese rol, sin modificar individualmente sus privilegios.

La cuenta sigue pudiendo consultar incidencias porque el rol conserva SELECT.

6️⃣ Retiramos un rol y lo eliminamos​

Debemos distinguir dos operaciones: quitarle un rol a una cuenta y eliminar el rol del servidor.

🔶 Retiramos un rol de una cuenta​

La sintaxis es:

REVOKE 'nombre_rol'@'host'
FROM 'usuario'@'host';

Paso 1. Retiramos el rol a tecnico2

Desde la consola administrativa de MySQL en la VM:

REVOKE 'rol_tecnico'@'%'
FROM 'tecnico2'@'localhost';

Paso 2. Consultamos sus asignaciones

SHOW GRANTS FOR 'tecnico2'@'localhost';

El resultado obtenido fue:

GRANT USAGE ON *.* TO `tecnico2`@`localhost`
en este ejemplo

Ya no aparece rol_tecnico. tecnico2 sigue existiendo como cuenta de MySQL, pero deja de tener asignados los privilegios de ese rol. La cuenta tecnico1 conserva la asignación.

🔶 Eliminamos un rol​

Si un rol deja de utilizarse, podemos eliminarlo mediante DROP ROLE.

Paso 1. Eliminamos el rol

DROP ROLE 'rol_tecnico'@'%';

Paso 2. Comprobamos que ya no existe

SHOW GRANTS FOR 'rol_tecnico'@'%';

En nuestro laboratorio, MySQL devolvió:

ERROR 1141 (42000): There is no such grant defined for user 'rol_tecnico' on host '%'
en este ejemplo

El rol ya no existe. DROP ROLE lo elimina del servidor y retira su asignación de todas las cuentas que lo tuvieran, incluida tecnico1. Las cuentas de los técnicos no se eliminan.

Estado del laboratorio

Al finalizar este apartado, las cuentas tecnico1 y tecnico2 siguen existiendo, pero el rol rol_tecnico ha sido eliminado.

Para volver a utilizarlo, será necesario crearlo, concederle privilegios y asignarlo nuevamente a las cuentas.

La base de datos soporte_tic conserva sus registros originales.

🔎 Para saber más: otras opciones de gestión de roles​

🔶 Activación de roles durante una sesión​

La instrucción SET ROLE permite cambiar los roles activos sin modificar sus asignaciones. Por ejemplo, para desactivar todos los roles durante la sesión:

SET ROLE NONE;

Para recuperar los roles predeterminados:

SET ROLE DEFAULT;

📖 Documentación oficial: uso y activación de roles

🔶 Consultar los privilegios incluidos en un rol asignado​

SHOW GRANTS muestra los roles concedidos, pero no siempre detalla sus privilegios. Con USING podemos consultar también los permisos que aporta un rol:

SHOW GRANTS FOR 'tecnico1'@'localhost'
USING 'rol_tecnico'@'%';

Este ejemplo requiere que el rol exista y siga asignado a la cuenta; no funcionará después de eliminarlo.

📖 Documentación oficial: SHOW GRANTS

7️⃣ ¿Qué hemos conseguido?​

Hemos aprendido a agrupar privilegios, asignarlos a varias cuentas y cambiar esos permisos sin modificar cada cuenta por separado.

NecesidadInstrucción
Crear un rol.CREATE ROLE
Asignar privilegios a un rol.GRANT privilegio ON ... TO rol
Asignar un rol a una cuenta.GRANT rol TO usuario
Activar el rol por defecto.SET DEFAULT ROLE
Comprobar el rol activo.SELECT CURRENT_ROLE()
Retirar privilegios de un rol.REVOKE privilegio ON ... FROM rol
Retirar un rol a una cuenta.REVOKE rol FROM usuario
Eliminar un rol.DROP ROLE
para pensar
