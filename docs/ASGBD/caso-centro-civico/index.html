🏢 Caso práctico · Centro Cívico La Estación

El Centro Cívico La Estación organiza actividades culturales y formativas para la ciudadanía. Dispone de dos sedes, Norte y Sur, con personal de recepción en cada una y una coordinación común.

Utilizaremos este caso desde la UT3 para aprender a configurar, proteger y administrar su sistema de bases de datos. Partimos del contexto conocido en UT0, ampliado para las necesidades de las prácticas de administración.

1️⃣ Cómo funciona el centro​

Las personas que participan se registran una sola vez como usuarios del centro. Su ficha es común a ambas sedes y pueden inscribirse en actividades de cualquiera de ellas. El alta se realiza en la recepción de cualquiera de las dos sedes.

Cada actividad pertenece a una sede y a un tipo de actividad, como formación, cultura o deporte. Tiene unas fechas de inicio y finalización, un número máximo de plazas y un estado: prevista, abierta, finalizada o cancelada.

Una inscripción relaciona a un usuario con una actividad. Conservamos la fecha de inscripción y su estado: activa o cancelada.

Las reglas de funcionamiento son:

  • Un usuario puede inscribirse en varias actividades.
  • Una actividad puede recibir inscripciones de varios usuarios.
  • Conservamos una única inscripción por usuario y actividad. Si se cancela o reactiva, actualizamos su estado.
  • Las inscripciones activas no deben superar las plazas disponibles.
  • Solo admitimos nuevas inscripciones en actividades abiertas.
  • Una inscripción cancelada no ocupa plaza, pero se conserva para mantener el historial.
  • En una actividad finalizada, una inscripción activa indica que la persona participó.
  • Los datos personales se utilizan únicamente por los perfiles que los necesitan para su trabajo.
Reglas del caso y controles del sistema

Algunas reglas ya están garantizadas por la base inicial mediante claves y restricciones. Las demás las implementaremos en las unidades indicadas.

¿Por qué no todas las reglas son restricciones?

Una restricción CHECK solo puede comprobar valores de la propia fila. Para saber si quedan plazas o si la actividad está abierta, hay que consultar otras filas y otras tablas. Por eso esas reglas necesitan mecanismos que veremos en UT7.

2️⃣ Qué información gestionamos​

Recibiremos la base de datos ya diseñada, con sus claves, relaciones y datos ficticios. Se llama centro_civico_asgbd. Comprenderemos su estructura para administrar el sistema y comprobar las operaciones.

TablaQué representaInformación principal
sedeLos centros Norte y Sur.Identificador, código, nombre, dirección y datos de contacto.
usuarioLas personas que participan en las actividades.Identificador, nombre, apellidos, correo, teléfono (opcional) y fecha de alta.
tipo_actividadLa clasificación de la oferta del centro.Identificador, nombre y descripción.
actividadLas actividades organizadas.Identificador, nombre, tipo, sede, fechas, plazas máximas y estado.
inscripcionLa participación de un usuario en una actividad.Identificador, usuario, actividad, fecha de inscripción y estado.
registro_cambio_inscripcionEl registro de cambios de estado de las inscripciones.Identificador, inscripción, fecha del cambio, estado anterior, estado nuevo y cuenta que ejecutó la operación.

Las relaciones principales son:

  • Una sede organiza varias actividades; cada actividad pertenece a una sede.
  • Un tipo de actividad clasifica varias actividades; cada actividad tiene un tipo.
  • Un usuario tiene varias inscripciones; cada inscripción corresponde a un usuario.
  • Una actividad tiene varias inscripciones; cada inscripción corresponde a una actividad.
  • Una inscripción puede tener varios registros de cambio.

La tabla de registro estará prevista desde el principio, vacía. Registrará solo los cambios de estado, es decir, cancelaciones y reactivaciones: crear una inscripción no genera registro. El mecanismo que la alimenta se desarrollará en UT7.

Datos ficticios

Todos los datos utilizados en las prácticas serán ficticios. No incorporaremos información personal real del alumnado ni de personas ajenas al laboratorio.

Estas necesidades se convertirán en cuentas, roles, permisos y mecanismos de acceso durante las prácticas. Comprobaremos tanto las operaciones permitidas como las que deben quedar denegadas.

Aplicaremos el principio de minimización de la normativa de protección de datos (RGPD y LOPDGDD): cada perfil accede solo a los datos personales que necesita para su trabajo.

Usuarios del centro y cuentas de MySQL

Los usuarios del centro son las personas que se inscriben en las actividades y aparecen en la tabla usuario.

Las cuentas de MySQL identifican a quienes se conectan al servidor o ejecutan tareas automáticas. Crear una fila en usuario no crea una cuenta de acceso al SGBD.

Además de las cuentas de los perfiles, crearemos cuentas técnicas con los privilegios mínimos para cada tarea: copias automáticas (UT6), monitorización (UT8) y replicación (UT11). La cuenta root solo se utilizará de forma local.

4️⃣ Nuestro punto de partida técnico​

La información de las dos sedes se guarda inicialmente en una base de datos centralizada en MySQL Server. Tener dos sedes no significa que ya exista una base distribuida.

En el laboratorio utilizaremos:

  • VMware como programa de virtualización.
  • Windows 11 Pro como sistema operativo de la VM creada en UT2.
  • MySQL Server 8.0 instalado y verificado dentro de esa VM.
  • Un cliente local dentro de la VM para las tareas de administración con root.
  • Workbench en el anfitrión, conectado a la VM con una cuenta limitada de laboratorio.

En UT3 configuraremos la conexión desde el anfitrión con una cuenta limitada; root seguirá siendo solo local. Más adelante utilizaremos instancias adicionales para las prácticas de distribución y replicación.

Antes de intervenir, comprobaremos que estamos conectados al servidor de la VM del laboratorio. Puede existir otra instalación de MySQL en el anfitrión utilizada en unidades anteriores.

Conservaremos la VM y los estados de recuperación acordados. Las instantáneas del laboratorio y las copias de la base de datos tienen funciones diferentes y no se sustituyen entre sí.

El caso se desarrollará progresivamente a lo largo del módulo. Mantendremos el escenario y las reglas básicas, e incorporaremos los recursos y configuraciones necesarios en cada etapa.

Ejecutamos los scripts 01, 02 y 03, en este orden, siguiendo el LEEME. Los ejecutamos desde cmd.exe, dentro de la VM, con mysql -u root -p < archivo.sql. Así se detienen ante el primer error.

No cargamos los datos con SOURCE

En el cliente interactivo (mysql>), SOURCE continúa después de un error y confirma lo que se haya cargado. Podríamos trabajar sobre una base incompleta sin darnos cuenta.

Al terminar, el script 03 debe mostrar 2 sedes, 12 usuarios, 3 tipos, 10 actividades, 20 inscripciones y 0 registros de cambio.

Recursos de las siguientes etapas

Cuando corresponda, facilitaremos datos adicionales para rendimiento, conjuntos de datos por sede y recursos para los montajes con varios servidores. Las fechas de las actividades forman parte de la simulación y no cambian con la fecha del ordenador: antes de UT7 recibiremos un script para actualizarlas.

Cada actividad indicará los archivos que debemos utilizar y el estado de partida del laboratorio. Si necesitamos actualizar la estructura o los datos, recibiremos el script y las instrucciones correspondientes.
