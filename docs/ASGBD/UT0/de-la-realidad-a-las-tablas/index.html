0.1 De la realidad a las tablas

Antes de consultar una base de datos necesitamos entender qué información queremos almacenar y cómo se relaciona.

En primero ya vimos que una base de datos no debería comenzar directamente creando tablas. Primero analizamos el problema real y construimos un modelo que represente la información que necesitamos.

RECORRIDO DE TRABAJO
🧩 Entendemos el problema→🧠 Identificamos la información→🔷 La representamos con un modelo E/R→🧱 La organizamos en tablas→✅ Definimos cómo deben ser los datos

Recordaremos, paso a paso, cómo pasar de una situación real a un modelo que podamos implementar posteriormente en una base de datos.

1️⃣ Recordamos el modelo E/R​

El modelo entidad-relación (E/R) nos permite representar de forma gráfica los elementos importantes de un problema y las relaciones que existen entre ellos.

Para este repaso necesitamos recordar cuatro elementos básicos.

🔸 Entidades​

Una entidad representa un objeto, persona, concepto o elemento del mundo real sobre el que queremos almacenar información.

Una entidad agrupa elementos que comparten las mismas características.

Por ejemplo, USUARIO representa a todos los usuarios que almacenaremos en nuestra base de datos.

En el diagrama E/R, las entidades se representan mediante un rectángulo.

🔸 Atributos​

Los atributos representan las características o propiedades que queremos almacenar de una entidad.

Por ejemplo, de un usuario podríamos guardar información como su nombre, correo o ciudad.

Cada atributo tendrá un valor concreto para cada elemento de la entidad.

En el diagrama E/R, los atributos se representan mediante un óvalo.

🔸 Identificadores​

Un identificador es un atributo que permite distinguir de forma única cada elemento de una entidad.

Por ejemplo, id_usuario puede utilizarse para identificar de forma única a cada usuario, aunque existan varios con el mismo nombre.

En el diagrama E/R, el atributo identificador se representa subrayado.

Más adelante, en el modelo relacional, este identificador se convertirá normalmente en una clave primaria.

🔸 Relaciones​

Las entidades no suelen aparecer aisladas. Una relación representa una asociación entre dos o más entidades.

Por ejemplo, un USUARIO puede inscribirse en una ACTIVIDAD.

Las relaciones permiten conectar la información de distintas entidades y representar cómo se vinculan entre sí.

En el diagrama E/R, las relaciones se representan mediante un rombo.

Para interpretar correctamente una relación debemos fijarnos también en su cardinalidad.

Las situaciones más habituales son:

  • 1:1 → un elemento se relaciona con uno solo del otro tipo.
  • 1:N → un elemento puede relacionarse con varios del otro tipo.
  • N:M → varios elementos pueden relacionarse con varios elementos del otro tipo.
tip

Para decidir la cardinalidad suele ser útil formular la relación en los dos sentidos.

Por ejemplo:

¿En cuántas actividades puede inscribirse un usuario?

¿Cuántos usuarios pueden inscribirse en una actividad?

2️⃣ Analizamos el problema​

Antes de dibujar un diagrama E/R conviene detenerse a comprender qué necesita realmente la organización y qué información será necesario almacenar.

En un proyecto real, normalmente no recibiremos una lista de tablas y atributos. Partiremos de una descripción del problema y tendremos que interpretarla, identificar los elementos importantes y detectar las reglas que debe cumplir el sistema.

¿Qué necesita gestionar la organización?

Lo primero es entender qué problema quiere resolver y qué información necesita controlar.

Debemos identificar qué procesos quiere gestionar, qué información necesita registrar y qué consultas o acciones deberá poder realizar posteriormente.

Estrategia

Antes de pensar en entidades o tablas, intenta resumir el problema en una frase:

“La organización necesita gestionar…”

Si no puedes completar esa frase con claridad, probablemente todavía no has entendido bien el problema.

¿Qué elementos intervienen?

A continuación debemos localizar los elementos principales que aparecen en el problema: personas, objetos, actividades, recursos, lugares, eventos, etc.

Un elemento puede ser un buen candidato a entidad cuando necesitamos almacenar información sobre varios elementos de ese tipo y distinguir unos de otros.

Para identificar posibles entidades

Pregúntate:

  • ¿Necesitamos registrar varios elementos de este tipo?

  • ¿Tenemos que guardar información propia de cada uno?

  • ¿Necesitamos distinguir unos de otros?

Si la respuesta es afirmativa, probablemente estamos ante una entidad.

¿Qué información necesitamos de cada elemento?

Una vez identificados los posibles elementos principales, debemos decidir qué información necesitamos almacenar de cada uno.

Esos datos se convertirán en sus atributos.

También tendremos que determinar qué dato, o conjunto de datos, permitirá identificar cada elemento de forma única.

No guardes datos porque sí

Un atributo debe responder a alguna necesidad del sistema.

Antes de añadirlo, pregúntate: ¿Para qué necesita la organización este dato?

¿Qué relaciones existen?

Los elementos del problema normalmente no aparecen aislados. Debemos analizar cómo se relacionan entre sí.

Una estrategia útil consiste en localizar los verbos del enunciado, ya que suelen expresar relaciones:

se inscribe, pertenece, realiza, reserva, organiza, contiene...

Después debemos estudiar la relación en los dos sentidos para determinar su cardinalidad.

Para determinar la cardinalidad

Formula siempre dos preguntas:

¿Con cuántos elementos de B puede relacionarse un elemento de A?

¿Con cuántos elementos de A puede relacionarse un elemento de B?

Las respuestas nos ayudarán a decidir si la relación es 1:1, 1:N o N:M.

¿Hay información que pertenezca a una relación?

En ocasiones aparece un dato que no describe únicamente a una entidad, sino que depende de la relación entre dos elementos.

Cómo detectarlo

Pregúntate si el valor del dato cambiaría dependiendo de con qué elemento se relaciona.

Si es así, probablemente estamos ante un atributo de la relación.

3️⃣ Del modelo E/R al modelo relacional​

Una vez construido el diagrama E/R, el siguiente paso consiste en transformarlo en un modelo relacional.

🔸 Antes de transformar: recordamos las claves​

  • Una clave primaria (PK) es el atributo, o conjunto de atributos, que permite identificar de forma única cada fila de una tabla. Sus valores no pueden repetirse ni ser nulos.

  • Una clave foránea (FK) es un atributo, o conjunto de atributos, que hace referencia a la clave primaria de otra tabla y permite establecer una relación entre ambas.

🔸 Reglas básicas de transformación​

Una vez definido el modelo E/R, necesitamos transformarlo en una estructura que pueda implementarse en un sistema gestor de bases de datos relacional. Para ello, cada elemento del modelo conceptual debe traducirse al modelo relacional siguiendo unas reglas básicas de transformación.

  • Entidad → tabla
  • Atributo de una entidad → columna
  • Identificador → clave primaria
  • Relación 1:N → normalmente, la clave primaria del lado 1 pasa como clave foránea al lado N
  • Relación N:M → nueva tabla intermedia con las claves de las entidades relacionadas
  • Los atributos propios de una relación también deben trasladarse al modelo relacional
Lista de comprobación

Antes de dar por terminada la transformación, revisa:

☐ Todas las entidades se han convertido en tablas.

☐ Cada tabla tiene una clave primaria.

☐ Las relaciones 1:N están representadas mediante una clave foránea.

☐ Las relaciones N:M se han convertido en una tabla intermedia.

☐ Los atributos de las relaciones se han trasladado correctamente.

🔸 Decidimos qué tipo de dato tendrá cada columna​

Una vez definidas las tablas y sus columnas, debemos pensar qué tipo de información almacenará cada una.

No todos los datos tienen la misma naturaleza. Podemos necesitar almacenar, por ejemplo:

  • números enteros
  • números decimales
  • texto
  • fechas
  • valores lógicos

Elegir correctamente el tipo de dato nos permite representar mejor la información y ayuda a evitar valores que no tienen sentido.

Por ejemplo:

  • un identificador puede almacenarse como un número entero
  • un nombre o un correo electrónico, como texto
  • una fecha de realización, como fecha
  • un precio, como un número decimal
¿Qué debemos preguntarnos?

Para cada columna, pregúntate:

¿Qué tipo de valor representa realmente este dato y qué operaciones necesitaremos realizar con él?

Por ejemplo, un teléfono contiene principalmente números, pero normalmente lo trataremos como texto, porque no vamos a realizar operaciones matemáticas con él.

Tipo de dato y SGBD

En esta fase estamos decidiendo qué naturaleza tiene cada dato.

Cuando llevemos el modelo a MySQL concretaremos esa decisión utilizando tipos propios del SGBD, como INT, VARCHAR, DATE o DECIMAL.

4️⃣ Restricciones: no todo vale​

Una vez definidas las tablas, sus columnas, las relaciones entre ellas y el tipo de información que almacenará cada columna, todavía tenemos que decidir qué valores vamos a permitir almacenar.

Las restricciones son reglas que deben cumplir los datos de una tabla.

Su objetivo es evitar datos incorrectos o incoherentes y ayudar a mantener la integridad de la información, es decir, que los datos almacenados sean válidos, coherentes y fiables y respeten las reglas definidas para la base de datos.

Por ejemplo, podemos decidir que plazas_maximas almacenará un número entero y, además, establecer que:

  • debe tener obligatoriamente un valor;
  • y ese valor debe ser mayor que 0.

Si intentamos realizar una operación que incumple alguna de estas reglas, el SGBD impedirá que se realice.

Ya hemos utilizado dos restricciones importantes:

  • PRIMARY KEY, para identificar de forma única cada fila.
  • FOREIGN KEY, para mantener las relaciones entre tablas.

Además, debemos recordar otras restricciones habituales.

🔸 NOT NULL​

Indica que una columna debe tener obligatoriamente un valor.

Si una columna admite NULL, significa que puede existir una fila en la que ese dato no esté informado.

¿Qué debemos preguntarnos?

¿Puede este dato quedar sin valor? Si la respuesta es no, probablemente necesitaremos utilizar NOT NULL.

🔸 UNIQUE​

Indica que el valor almacenado en una columna no puede repetirse en distintas filas.

¿Qué debemos preguntarnos?

¿Puede haber dos registros diferentes con el mismo valor? Si ese valor debe ser diferente para cada registro, necesitaremos utilizar UNIQUE.

🔸 CHECK​

Permite establecer una condición que deben cumplir los valores almacenados en una columna.

Nos permite representar determinadas reglas que deben respetarse para que los datos sean válidos.

Por ejemplo, si una columna almacena una cantidad, podemos establecer que su valor debe ser mayor que 0.

¿Qué debemos preguntarnos?

¿Qué condiciones debe cumplir este dato para que su valor sea válido?

Podemos necesitar controlar límites, rangos o determinados valores permitidos.

🔸 DEFAULT​

Permite establecer un valor por defecto que se utilizará cuando al insertar una fila no se proporcione ningún valor para esa columna.

¿Qué debemos preguntarnos?

¿Existe algún valor que podamos asignar automáticamente cuando no se indique otro?

El valor por defecto debe tener sentido para la mayoría de los casos; no se utiliza simplemente para evitar introducir un dato.

Tipo de dato y restricción no son lo mismo

Para cada columna debemos tomar dos decisiones diferentes:

  1. ¿Qué tipo de información almacenará?
  2. ¿Qué reglas deberán cumplir sus valores?

Por ejemplo:

cantidad

  • tipo de dato → número entero;
  • obligatorio → NOT NULL;
  • debe ser mayor que 0 → CHECK.
Del diseño a MySQL

En este apartado decidimos qué restricciones necesita nuestro modelo.

En el siguiente apartado veremos cómo trasladar estas decisiones a MySQL utilizando PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, CHECK o DEFAULT al crear las tablas.

5️⃣ En resumen​

Antes de implementar una base de datos en un SGBD, debemos recorrer varias etapas.

1. Analizamos la realidad que queremos representar

Identificamos qué necesita gestionar la organización, qué elementos intervienen y qué información necesitamos almacenar.

2. Construimos el modelo E/R

Representamos las entidades, sus atributos, los identificadores, las relaciones y sus cardinalidades.

3. Transformamos el modelo E/R al modelo relacional

Convertimos las entidades en tablas, los atributos en columnas y representamos las relaciones mediante claves foráneas o tablas intermedias.

4. Definimos las restricciones

Establecemos las reglas que deben cumplir los datos para evitar valores incorrectos o incoherentes.

Idea clave

El diseño de una base de datos no comienza escribiendo instrucciones SQL.

Primero debemos comprender la realidad que queremos modelar, organizar la información y definir las reglas que deberá respetar.
