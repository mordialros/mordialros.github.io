1.4. Identificamos nuestra instalación

Antes de administrar un sistema, necesitamos identificarlo. Tener una conexión llamada «MySQL local» no nos dice por sí solo qué versión está funcionando ni qué cuenta estamos utilizando.

Vamos a reconocer el cliente, el servicio, el servidor al que nos conectamos y nuestra sesión. Utilizamos la instalación que ya tenemos: no necesitamos reinstalar MySQL ni crear tablas para realizar estas comprobaciones.

1️⃣ Reconocemos el cliente y el servicio​

🔸 La versión de Workbench​

Workbench y MySQL Server son programas diferentes y tienen versiones propias. En la ventana de información de Workbench, normalmente accesible desde Help → About MySQL Workbench en Windows, podemos consultar la versión del cliente.

Ese número no demuestra qué versión del servidor estamos utilizando. Una misma herramienta puede guardar conexiones a distintos servidores.

🔸 El servicio de MySQL en Windows​

En los equipos Windows del aula podemos localizar el servicio instalado:

  1. Pulsamos Windows + R, escribimos services.msc y aceptamos.
  2. Buscamos el servicio correspondiente a MySQL. Su nombre depende de cómo se haya instalado; no suponemos que todos los equipos tengan el mismo.
  3. Anotamos su nombre y comprobamos su estado.

El estado En ejecución indica que ese servicio está iniciado. El tipo de inicio indica cómo se inicia, por ejemplo automáticamente al arrancar Windows. Son datos diferentes.

Si consultamos las propiedades del servicio, la ruta del ejecutable ayuda a identificar la instalación asociada. No necesitamos cambiar ninguna propiedad.

Idea clave

Esta comprobación se refiere al equipo donde abrimos la herramienta Servicios. Si Workbench se conecta a otro ordenador, los servicios de nuestro Windows no muestran el estado del servidor remoto.

2️⃣ Preguntamos al servidor quién es​

Abrimos nuestra conexión habitual en Workbench y una pestaña de consultas. Seleccionamos y ejecutamos cada bloque por separado para relacionarlo con su resultado.

SELECT
    VERSION() AS version_servidor,
    @@hostname AS nombre_equipo_servidor,
    @@port AS puerto_servidor;
en este ejemplo

VERSION() devuelve la versión del servidor que responde. @@hostname y @@port consultan variables del sistema del servidor. AS asigna una etiqueta a cada columna del resultado para facilitar su lectura.

No necesitamos escribir FROM porque estamos consultando funciones y variables, no filas de una tabla.

ResultadoCómo lo interpretamos
version_servidor.Anotamos la versión real, incluido cualquier sufijo relevante. No copiamos la versión de Workbench.
nombre_equipo_servidor.Es el nombre de equipo que informa el servidor. No tiene por qué coincidir con la etiqueta de la conexión ni con la dirección escrita en Hostname.
puerto_servidor.Es el puerto configurado para el protocolo clásico de MySQL en ese servidor. En nuestra conexión local directa debería coincidir con el indicado en Workbench.

Los resultados pueden variar entre equipos. No existe un nombre de servidor ni un número de versión que todo el grupo deba obtener.

para pensar

Dos personas tienen la misma versión de Workbench, pero VERSION() devuelve valores diferentes. ¿Es necesariamente un error? ¿Qué programa estamos identificando en cada caso?

3️⃣ Identificamos nuestra sesión​

Una sesión es el contexto de trabajo asociado a nuestra conexión: incluye la identidad con la que accedemos y opciones como la base de datos seleccionada.

SELECT
    USER() AS identidad_conexion,
    CURRENT_USER() AS cuenta_autenticada,
    DATABASE() AS base_datos_actual;
en este ejemplo

En esta consulta directa, USER() muestra el usuario indicado al conectar y el origen del cliente que observa el servidor. CURRENT_USER() muestra la cuenta que MySQL ha utilizado para autenticarnos. DATABASE() devuelve la base de datos seleccionada en esta sesión.

🔸 Usuario presentado y cuenta autenticada​

Los valores de USER() y CURRENT_USER() pueden coincidir, pero expresan cosas distintas. MySQL identifica sus cuentas mediante una combinación de usuario y origen permitido. Por eso no debemos interpretar el texto situado después de @ como el nombre de una base de datos.

Por ahora nos basta con reconocer la cuenta utilizada. La creación de cuentas y la asignación de permisos se estudiarán más adelante.

🔸 Base de datos seleccionada​

Si DATABASE() devuelve NULL, no hay una base de datos predeterminada seleccionada en esa sesión. Eso no significa que el servidor esté vacío ni que la conexión haya fallado.

Para comprobar el cambio:

  1. Localizamos en SCHEMAS la base de datos del centro cívico, si ya está creada.
  2. Hacemos doble clic en su nombre para seleccionarla.
  3. Ejecutamos de nuevo SELECT DATABASE(); en esa conexión.

El resultado debe mostrar el nombre real de la base seleccionada. Si todavía no tenemos la base del repaso, podemos continuar con las consultas de identificación sin crearla.

para pensar

La consulta de versión funciona y DATABASE() devuelve NULL. ¿Tenemos conexión con el servidor? ¿Qué nos falta seleccionar?

4️⃣ Localizamos los datos y reconocemos los esquemas​

Contenido complementario

La consulta del directorio de datos y el reconocimiento de los esquemas del sistema sirven para familiarizarnos con el entorno real del servidor. Si el tiempo es limitado, podemos considerarlos una ampliación: lo imprescindible en esta unidad es identificar la conexión, el servidor, la sesión y la base de datos seleccionada. No modificamos nunca estos esquemas.

🔸 El directorio de datos​

SELECT @@datadir AS directorio_datos;
en este ejemplo

@@datadir informa del directorio de datos configurado en el servidor. La ruta pertenece al equipo donde se ejecuta MySQL Server, aunque lancemos la consulta desde Workbench en otro ordenador.

El directorio de datos no es la carpeta donde guardamos nuestros archivos .sql. Un script contiene instrucciones; el gestor mantiene los datos y sus estructuras mediante su propia organización de almacenamiento. Además, determinados archivos pueden ubicarse fuera del directorio principal según la configuración.

Identificar no es modificar

No borramos ni movemos los archivos del directorio de datos manualmente. Tampoco consideramos que copiar esa carpeta con el servidor funcionando sea, por sí solo, una copia de seguridad válida. Aprenderemos a realizar y comprobar las copias con el procedimiento adecuado.

🔸 Las bases de datos visibles​

SHOW DATABASES;
en este ejemplo

La instrucción muestra las bases de datos visibles para nuestra cuenta. La lista depende de los permisos, por lo que dos cuentas conectadas al mismo servidor pueden obtener resultados diferentes.

En MySQL, schema y database se utilizan como sinónimos. Por eso Workbench agrupa las bases de datos bajo SCHEMAS. Este uso de la palabra no significa que cada elemento del panel sea un nivel de ANSI/SPARC.

Además de nuestras bases de datos, podemos encontrar esquemas del sistema:

EsquemaPara qué sirve
mysql.Contiene información utilizada por el servidor, como datos relacionados con cuentas y privilegios.
information_schema.Ofrece metadatos consultables sobre objetos como tablas y columnas.
performance_schema.Recoge información de instrumentación sobre la ejecución del servidor.
sys.Ofrece vistas y otros objetos que facilitan la interpretación de información de diagnóstico.

No son bases de datos creadas para nuestras actividades. Su visibilidad depende del entorno y de los permisos; no debemos eliminarlas ni modificar sus tablas directamente para «limpiar» la instalación.

5️⃣ Dejamos constancia de lo que hemos identificado​

Una pequeña ficha técnica nos permite describir el entorno sin depender de lo que recordamos de la instalación.

Dato que documentamosDónde lo comprobamos
Versión del cliente Workbench.Ventana de información del programa.
Destino y puerto de la conexión.Parámetros guardados en Workbench.
Nombre y estado del servicio local, si corresponde.Servicios de Windows.
Versión, nombre del equipo y puerto del servidor.Consulta de identificación del servidor.
Cuenta autenticada y base seleccionada.Consulta de identificación de la sesión.
Directorio de datos del servidor.Consulta de @@datadir.

Anotamos valores reales y distinguimos los datos del cliente de los del servidor. No incluimos contraseñas en la ficha ni en las capturas.

Este procedimiento servirá de apoyo para la actividad «Radiografía de nuestra instalación», cuyo enunciado estará en el apartado de actividades de la UT1.

Antes de continuar
  • Sabemos qué cliente utilizamos y qué servidor responde.
  • Distinguimos la etiqueta de una conexión del nombre del servidor y de la base de datos.
  • Interpretamos NULL en DATABASE() como ausencia de selección, no como fallo de conexión.
  • Reconocemos que las rutas devueltas por el servidor pertenecen a su equipo.
  • Registramos los resultados de nuestra instalación sin dar por supuestos los valores del ejemplo.
