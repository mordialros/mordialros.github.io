5.1. Del diseño lógico al diseño físico

En las unidades anteriores hemos aprendido a diseñar bases de datos. Ya sabemos qué tablas necesitamos, qué atributos contienen y cómo se relacionan. Ahora vamos a convertir ese diseño en una base de datos que funcione en MySQL.

1️⃣ Del diseño lógico al diseño físico​

El diseño lógico describe la estructura de los datos con independencia del SGBD. El diseño físico concreta cómo se implementará esa estructura en el gestor elegido.

Diseño lógicoDiseño físico en MySQL
Atributo nombre de CLIENTEColumna nombre de tipo VARCHAR(80)
Identificador de CLIENTEPRIMARY KEY
Relación entre EQUIPO y CLIENTEFOREIGN KEY en equipo
Presupuesto no negativoRestricción CHECK
Tabla CLIENTETabla almacenada mediante InnoDB

No vamos a volver a diseñar el modelo E/R ni a normalizarlo: partiremos de un modelo relacional y tomaremos las decisiones necesarias para implementarlo.

2️⃣ ¿Cómo se almacenan los datos?​

Cuando creamos una tabla, MySQL no guarda los datos en una hoja de cálculo. El servidor utiliza estructuras internas y archivos para almacenarlos y recuperarlos.

Un motor de almacenamiento es el componente de MySQL que se encarga de organizar el almacenamiento y el acceso a los datos de una tabla. Podemos elegirlo al crear cada tabla.

CaracterísticaInnoDBMyISAM
Motor predeterminado en MySQL 8.4SíNo
Claves foráneasLas aplicaNo las aplica
TransaccionesSíNo
Archivos habituales.ibd (datos e índices, con la configuración predeterminada).MYD (datos) y .MYI (índices)

Utilizaremos InnoDB porque necesitamos que MySQL garantice la integridad referencial entre las tablas.

🔶 Archivos y espacios de tablas​

Un espacio de tablas (tablespace) es una estructura de almacenamiento de InnoDB respaldada por uno o varios archivos. Puede almacenar información de una tabla o de varias, según su configuración.

Con la configuración predeterminada, cada tabla de usuario de InnoDB se almacena normalmente en su propio archivo .ibd, que contiene sus datos e índices. Por ejemplo, al crear una tabla cliente, podremos encontrar un archivo cliente.ibd dentro del directorio de la base de datos.

Vamos a comprobar algunas características de nuestro servidor. Abre la conexión local en Workbench y ejecuta estas sentencias:

SELECT @@default_storage_engine;
SELECT @@datadir;
SELECT @@innodb_file_per_table;
SentenciaQué nos permite comprobar
SELECT @@default_storage_engine;Motor predeterminado: normalmente InnoDB.
SELECT @@datadir;Directorio de datos del servidor.
SELECT @@innodb_file_per_table;Si se utiliza un espacio de tablas individual de forma predeterminada: normalmente 1 (activado).

Estas consultas solo muestran información; no modifican la configuración del servidor.

Los archivos de datos los gestiona MySQL

No abras, muevas ni elimines manualmente los archivos internos de las bases de datos. Trabajaremos siempre a través de MySQL Server, utilizando SQL o las herramientas gráficas de Workbench.

3️⃣ ¿Qué son los índices?​

Un índice es una estructura que ayuda al SGBD a localizar registros sin tener que recorrer necesariamente toda la tabla.

Imagina que un servicio técnico tiene miles de equipos registrados y queremos localizar uno por su número de serie. Un índice sobre esa columna puede facilitar la búsqueda.

Los índices también ocupan espacio y deben mantenerse cuando cambian los datos. Por eso no se crean indiscriminadamente.

MySQL crea índices para determinadas claves y restricciones. Volveremos a este concepto cuando implementemos las claves primarias, alternativas y foráneas y comprobaremos los índices mediante SHOW INDEX.

4️⃣ Nuestro caso práctico: TechRepair​

TechRepair es un servicio técnico informático que necesita gestionar sus clientes, los equipos que recibe y las reparaciones realizadas. Una reparación puede requerir varias intervenciones de distintos técnicos.

Partiremos de estas cinco tablas:

TablaAtributosClaves
CLIENTEid_cliente, nombre, email, telefonoPK: id_cliente; alternativa: email
EQUIPOid_equipo, numero_serie, marca, modelo, id_clientePK: id_equipo; alternativa: numero_serie; FK: id_cliente → CLIENTE
TECNICOid_tecnico, nombre, especialidad, fecha_altaPK: id_tecnico
REPARACIONid_reparacion, id_equipo, descripcion, fecha_entrada, fecha_cierre, estado, presupuestoPK: id_reparacion; FK: id_equipo → EQUIPO
INTERVENCIONid_reparacion, id_tecnico, fecha_hora, descripcion, minutosPK: (id_reparacion, id_tecnico, fecha_hora); FK: id_reparacion → REPARACION; FK: id_tecnico → TECNICO

🔶 Reglas del problema​

  • Cada equipo pertenece a un cliente y tiene un número de serie único.
  • Cada reparación corresponde a un equipo. Un equipo puede tener varias reparaciones.
  • Los técnicos pueden intervenir varias veces en una reparación, en momentos diferentes.
  • El correo del cliente es obligatorio y único; su teléfono es opcional.
  • Una reparación comienza en estado pendiente; los estados admitidos son pendiente, en_proceso y cerrada.
  • El presupuesto puede estar pendiente de determinar; si se conoce, no puede ser negativo.
  • La fecha de cierre es opcional y, si existe, no puede ser anterior a la de entrada. Una reparación cerrada debe tener fecha de cierre y las demás no deben tenerla.
  • Cada intervención tiene una descripción y una duración positiva en minutos.
  • Los demás atributos son obligatorios.
  • No se eliminarán clientes, equipos, reparaciones ni técnicos mientras existan registros que los referencien.

A lo largo de la unidad implementaremos este modelo y lo ampliaremos para practicar otras situaciones, como las claves foráneas compuestas y las relaciones 1:1.

La primera decisión de diseño físico

Ya sabemos qué motor utilizaremos para nuestras tablas: InnoDB. En los próximos apartados aprenderemos a crear la base de datos, elegir los tipos de datos y definir las claves y restricciones del modelo.
