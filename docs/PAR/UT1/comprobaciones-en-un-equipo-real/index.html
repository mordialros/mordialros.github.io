1.8. Comprobaciones en un equipo real

Hasta ahora hemos aprendido a reconocer los elementos de una red y a distinguir las direcciones MAC e IP. Vamos a comprobar cómo está conectado un equipo real y qué podemos averiguar cuando intentamos comunicarnos con otros dispositivos.

Utilizaremos tres comandos de Windows: ipconfig, ping y tracert. Si trabajamos con una máquina virtual, los resultados pueden ser diferentes de los obtenidos en el equipo físico.

Idea clave

No buscamos memorizar comandos ni resolver cualquier avería de red. Vamos a observar resultados, interpretarlos y distinguir lo que podemos afirmar de lo que todavía no sabemos.

Para abrir la consola de Windows, podemos escribir cmd en el buscador del menú Inicio y abrir Símbolo del sistema. No necesitamos permisos de administrador para estas comprobaciones.

1️⃣ ipconfig: ¿cómo está configurado mi equipo?​

En la consola escribimos:

ipconfig /all
en este ejemplo

Este comando muestra información de las interfaces de red del equipo. Puede aparecer más de una: Ethernet, Wi-Fi, adaptadores virtuales u otras interfaces. Buscamos la que estemos utilizando y no damos por hecho que todas están conectadas.

Estos son los datos más útiles para empezar:

Dato¿Qué nos indica?
DescripciónEl nombre o tipo de adaptador de red.
Dirección físicaLa dirección MAC de esa interfaz.
DHCP habilitadoSi la interfaz está preparada para obtener automáticamente determinados parámetros de red. No demuestra por sí solo que se haya recibido una configuración válida.
Dirección IPv4La dirección IP asignada a esa interfaz.
Máscara de subredAyuda a distinguir qué direcciones pertenecen a la misma red. La estudiaremos con detalle en la UT4.
Puerta de enlace predeterminadaLa dirección del dispositivo al que el equipo envía normalmente la información destinada a otras redes. Suele ser un router.
Servidores DNSLos servidores que pueden ayudar a obtener la dirección IP asociada a nombres como www.example.com.
Ejemplo

Un ordenador podría mostrar una dirección IP 192.168.1.25, una máscara 255.255.255.0 y una puerta de enlace 192.168.1.1.

Son valores de ejemplo. En nuestro ordenador pueden aparecer otros. Por ahora nos interesa saber identificar cada dato, no calcular redes a partir de la máscara.

¿Y si utilizamos una máquina virtual?

Una máquina virtual puede disponer de interfaces de red virtuales. Por eso, los datos mostrados por ipconfig /all pueden ser diferentes de los del equipo físico.

En esta unidad nos limitaremos a observar su configuración, sin modificarla.

2️⃣ ping: ¿recibimos respuesta?​

El comando ping envía mensajes de prueba a un destino y comprueba si recibe respuesta. Ya lo utilizamos de manera introductoria en la UT0; ahora vamos a interpretar mejor sus resultados.

Podemos comenzar por una dirección conocida de nuestra propia red, por ejemplo la puerta de enlace obtenida con ipconfig /all:

ping 192.168.1.1
en este ejemplo

192.168.1.1 es solo un ejemplo. Debemos sustituirlo por la dirección de la puerta de enlace que aparezca en nuestro equipo. Si no hay ninguna configurada, no inventamos una.

Si disponemos de conexión a Internet, podemos probar después:

ping 8.8.8.8

Y, para comprobar si el equipo puede utilizar un nombre en lugar de escribir directamente una dirección IP:

ping www.example.com
Resultado observado¿Qué podemos interpretar?
Respuesta desde…Hemos recibido una respuesta del destino o del equipo indicado. El comando también muestra el tiempo empleado.
Tiempo de espera agotadoNo hemos recibido respuesta dentro del plazo. No significa necesariamente que el destino esté apagado: puede haber filtros o restricciones.
Host de destino inaccesibleAlgún equipo nos informa de que no puede alcanzar el destino. Necesitamos más comprobaciones para identificar la causa.
No se pudo encontrar el hostNo se ha podido obtener una dirección para el nombre indicado. Puede existir un problema de resolución de nombres o un error al escribirlo.
warning

Un ping fallido no identifica por sí solo dónde está la avería. Por ejemplo, algunos dispositivos están configurados para no responder a estos mensajes aunque otros servicios de red funcionen correctamente.

Asimismo, que ping 8.8.8.8 responda y una prueba por nombre falle sugiere revisar la resolución DNS, pero no demuestra por sí solo cuál es la causa.

3️⃣ tracert: ¿qué recorrido observamos?​

El comando tracert intenta mostrar los saltos intermedios que aparecen al comunicarnos con un destino. Un salto es el paso por un dispositivo que encamina la información hacia otra red, normalmente un router.

tracert www.example.com
en este ejemplo

El resultado suele mostrar una sucesión de saltos y tiempos de respuesta. El primer salto visible puede corresponder a nuestra puerta de enlace, pero no tiene por qué aparecer siempre. Un asterisco (*) indica que no se recibió respuesta a una de las pruebas dentro del tiempo previsto.

No debemos interpretar cada asterisco como una avería ni asumir que la lista muestra necesariamente todos los dispositivos por los que circula la información.

4️⃣ Comprobamos e interpretamos​

En nuestro equipo, sin cambiar ninguna configuración, seguimos este orden:

  1. Abrimos la consola y ejecutamos ipconfig /all. Identificamos la interfaz que estamos utilizando y localizamos, si aparecen, su MAC, dirección IP y puerta de enlace.
  2. Ejecutamos ping hacia una dirección de nuestra red que conozcamos, preferentemente la puerta de enlace si está disponible. Observamos si hay respuesta.
  3. Si el equipo dispone de acceso a Internet, probamos ping 8.8.8.8 y ping www.example.com. Comparamos los resultados.
  4. Ejecutamos tracert www.example.com y observamos los saltos y los posibles asteriscos.
para pensar

Dos equipos ejecutan ping www.example.com. Uno recibe respuesta y el otro muestra «Tiempo de espera agotado».

¿Podemos asegurar que el segundo equipo no tiene conexión a Internet? ¿Qué otra comprobación realizaríamos antes de sacar una conclusión?

Idea clave
  • Con ipconfig /all consultamos cómo están configuradas nuestras interfaces de red.
  • Con ping comprobamos si recibimos respuestas a mensajes de prueba.
  • Con tracert observamos parte del recorrido hacia un destino.

Estas herramientas aportan pistas para diagnosticar problemas, pero debemos interpretar sus resultados antes de afirmar cuál es la causa de un fallo.
